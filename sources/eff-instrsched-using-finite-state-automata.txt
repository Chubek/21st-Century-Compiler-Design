In the rst method, the compiler maintains a list of

already committed in the current and future cycles.

Modern compilers employ sophisticated instruction
scheduling techniques to shorten the number of cycles
taken to execute the instruction stream. In addition to
correctness, the instruction scheduler must also ensure
that hardware resources are not oversubscribed in any
cycle. For a contemporary processor implementation
with multiple pipelines and complex resource usage restrictions, this is not an easy task. The complexity involved in reasoning about such resource hazards is one
of the primary factors that constrain the instruction
scheduler from performing many aggressive transformations. For example, the ability to do code motion
or instruction replacement in the middle of an already
scheduled block would be a very powerful transformation if it could be performed eciently. We extend a
technique for detecting pipeline resource hazards based
on nite state automata, to support the ecient implementation of such transformations that are essential for aggressive instruction scheduling beyond basic
blocks. Although similar code transformations can be
supported by other schemes such as reservation tables,
our scheme is superior in terms of space and time. A
global instruction scheduler that used these techniques
was implemented in the KSR compiler.

1 Introduction

A legal instruction schedule must be free of data,
control and structural hazards. Structural hazards refer to the contention for hardware resources by instructions executing in the pipelines. Some hardware implementations cause a pipeline stall when structural hazards are detected, while others require the compiler to
insert explicit NOP instructions in the stream to prevent such hazards from occuring. Both approaches are
equivalent in the sense that a pipeline stall causes a
bubble in the pipeline ow, which has the same e ect
as a statically introduced NOP instruction. The techniques discussed in this paper deal primarily with the
detection and avoidance of structural hazards in the
compiler's instruction scheduling phase.

the automaton transition table to check if the current

show that it can also be used to drive a sophisticated
global instruction scheduler. For instance, a suitably
modi ed automaton can give the instruction scheduler
the ability to insert an instruction into the middle of
an already scheduled block. This feature allows more
ecient placement of compensation code that gets generated when an instruction is speculatively scheduled
above a branch upon which it is control dependent.

2.1 States and Transitions

In the Muller automaton [9], each state corresponds
to a resource reservation table. The reservation table
explicitly models each resource. It is represented by
a bit matrix of size number of resources  length of
the longest pipe. The value at position i; j of state S
speci es whether the i'th resource will be used j cycles
in the future.
Each instruction I is described by a similarly shaped
matrix: the value at position i; j speci es whether instruction I uses the i'th hardware resource j cycles
after it is launched. Often, it is the case that several instructions share the same reservation table. For
example, the Alpha 21064 processor requires only 10
distinct reservation tables. In the remainder of the paper we will use the term instruction class to refer to
the set of instructions that share the same bit matrix
representation.
Given a state S and an instruction I, it is legal to issue I at this pipeline state only if the reservation table
for I does not have any bits set that are also set in the
reservation table corresponding to S. If0 legal to issue,

tables for S and I.
Sometimes additional information may be required
to fully describe the rules of instruction issue. For example on some processors, instructions may be multiissued only if special alignment rules are followed.
Therefore, a state may need an additional bit indicating if the next instruction will be placed at a multiissue boundary.

Certain states in the automaton correspond to situations in which the hardware pipeline clock advances
to the next cycle. On a single-issue machine such as
the MIPS R3000, this happens after the issue of every instruction. On a multi-issue machine this happens when either all instruction decode units are in use

in all the pipelines.

The Finite State Automaton discussed above recognizes all legal sentences (instruction schedules) in this
language.

Since the automaton produced by algorithm BuildForwardFSA recognizes legal instruction schedules

Instruction scheduling algorithms can be implemented in one of two basic avors. The rst, called
cycle scheduling, schedules the current cycle with instructions before moving on to the next one. The second approach, called operation scheduling schedules instructions in priority order, placing them in the earliest
legal cycle where their resource demand is satis ed.
The applicability of the automaton in the cycle
scheduling scheme is straightforward. Given a starting
automaton state, the instruction scheduler scans some
priority queue of ready instructions (i.e., those whose
input operands are available in the current cycle), and
schedules the rst one that allows a transition from
the current state. The automaton state is updated to
the new state, and the process is repeated. This will
guarantee a schedule that is free of structural hazards.
In order to use the automaton for the operation
scheduling scheme, we can model the scheduling process as lling a table of empty instruction slots extending into the future. This initial \table of empty
instruction slots" corresponds to a sentence consisting only of NOPs. Operation scheduling is then the
repeated transformation of this initial sentence by replacing speci c NOPs with instructions, such that no
structural hazards are created at any step.
The techniques discussed in this paper for instruction scheduling using nite state automata apply
equally well for either implementation scheme. In the
remainder of this paper we will assume that the compiler implements the cycle scheduling scheme since it
is easier to discuss.
We also assume that as the instruction scheduler
schedules a block, it records the automaton state transitions for later use. Figure 3 shows an example that
illustrates this. Blocks B1 and B2 show the scheduled instruction sequences, with the forward automaton transitions listed on their left. Notice that a basic
block always ends in a cycle-advancing state of F. This
is because the instruction scheduler cannot break an
instruction cycle (or a VLIW instruction word) across
a basic block boundary.
If the traditional reservation table bit matrices were
recorded in the schedule instead of these automaton
states, the space requirement would be signi cantly
increased. For instance, the reservation table for the
Alpha 21064 would be a bit matrix of size 6  59 (6
resources, and a maximum pipeline length of 59 cycles for the fdivq class of instructions). That means
about 48 bytes of storage to record a single reservation
table, compared to the automaton which requires only
4 bytes (for the integer representing the automaton
state) to record the equivalent amount of information.
Thus, in the example in Figure 3, recording the forward automaton states for the schedule in Block B1
requires 11  4 = 44 bytes, while recording the reservation table bit matrices would require 11  48 = 528
bytes.
The key insight here is that the instruction sched-

uler really wants a mechanism to reason about sentences (schedules), and not about hardware resource
usage. The automaton is merely a schedule recognition
machine that eciently answers questions about what
suxes can follow a legal schedule without introducing
structural hazards. It can detect a structural hazard,
but cannot determine what hardware resource(s) are
responsible for its occurance, or at which cycle the actual hazard will occur.

3.1 Basic Block Boundaries

Before scheduling a basic block, the instruction
scheduler needs to determine the automaton state at
which to start. If the block has no scheduled predecessors, the state F0 is used as the starting state. State
F0 is the least restrictive of the forward automaton
states, since any instruction can be issued from this
state.
The tricky part is deciding the starting state for a
block that has more than one predecessor (i.e., a join
block), that has already been scheduled. A complimentary problem is determining a legal ending automaton
state for the block if one or more of its successors has
already been scheduled earlier.
The solution to these problems are related, since we
cannot allow structural hazards to occur when execution crosses a basic block boundary.
One simple solution is to never allow resources to
be in use across a basic block boundary. The automaton state at the top of every block could be the empty
start state, and at the end of the block enough NOP
instructions can be issued until all pipes are quiesced
(i.e., we wind up at the empty start state of the automaton F). The problem with this solution is that
sparsely lled cycles will be created at the end of basic
blocks, resulting in inecient code.
A better solution is to derive the start state at the
top of a join block (called the join state) by OR-ing together the automaton states (i.e., their collision matrix
representations) at the end of its predecessor blocks.
The problem here is that the join state produced as a
result may not even belong to the forward automaton
F produced by algorithm BuildForwardFSA. The reason is that such a join state represents the con uence
of several pre x sentences in the language recognized
by the automaton F, and this may not be a sentence
in the language recognized by F. This can be rectied by making a suitable modi cation to Algorithm
BuildForwardFSA as discussed below.

3.2 The Join Table

We noted earlier that all scheduled blocks must end
in a cycle-advancing state of F. Consider the set of all
pairs of cycle-advancing states in the forward automaton F. If we OR-ed together the collision matrices of
each pair, we would get a new set of states that correspond to all possible pairwise combinition of states of
F that the scheduler could encounter at the start of a
join block.

such join states (the table is symmetric about the principal diagonal due to the commutativity of the OR
operation on collision matrices). Algorithm BuildForwardFSA can be modi ed to compute these join states
on the y. Each time a new cycle-advancing state is
created, its collision matrix is OR-ed with that of all

This join state is also added to the state hashtable

new states list, there will be outgoing transitions

But how do we get to the appropriate join state?
One way to do this is to maintain a square table with
number of rows (and columns) equal to the number of

the join table of F. In our example, the join state for

the identity for the Join relation. Any unscheduled
predecessor block is assumed to end in the state F0.
The join table thus allows the instruction scheduler
to select an appropriate join state from which to start
scheduling a join block, given the ending automaton
states at the bottom of its predecessors. This works
because the join of two states is a more restrictive state
than either of them, in the sense that everything that
is an illegal sux of either state is also an illegal sufx of the join state. This is guaranteed by the construction of the join state in the modi ed Algorithm
BuildForwardFSA. Once we have a join state in F, the
usual scheduling algorithm of \issue a NOP if nothing
else ts" will generate a schedule that is compatible
with the incoming states from the predecessor blocks.
If a join block has more than two predecessors, the
join state is determined in a pairwise manner using
the join table, with each subsequent lookup of the join
table yielding a more restrictive join state.
If information about block execution frequencies is
available to the compiler, and one of the predecessors
of a join block is not frequently executed, the compiler
can opt to issue NOPs at the end of that predecessor
block until it reaches the F0 state.
Sometimes it is the case that both incoming states
to a join block represent the situation where there is
a very long instruction currently in ight (such as a
divide or square root). This may cause the scheduler
to follow a large number of NOP transitions starting
from the join state before it actually gets to issue a real
instruction. The number of additional states created
by the modi ed Algorithm BuildForwardFSA may also

increase signi cantly. However, if we assume that this
scenario represents a somewhat rare event, we can optimize our representation of join tables by zeroing out
the collision matrix of every join state beyond some
cycle k, as soon as it is synthesized by the modi ed
Algorithm BuildForwardFSA. In other words, we only
model at most k NOP transitions going out of any join
state, and beyond that point we will rely on the hardware to stall the pipeline to prevent any structural hazards from occurring. This will not reduce the number
of join states, but it will lower the number of additional
states created by algorithm BuildForwardFSA corresponding to collision matrices derived by transitions
starting from the join states. Obviously this scheme
works only on processors that have hardware interlock
support to stall the pipeline in case of a structural hazard.

4 Scheduling Beyond Basic Blocks

One of the problems in designing a global instruction scheduler (i.e., one that speculates instructions
updwards past basic block boundaries), is guring out
how to handle compensation code. Global instruction
schedulers typically select a path in the control ow
graph (called a \trace") based on various heuristics,
and then move one or more instructions in the trace
up toward the top in order to shorten the number of
execution cycles incurred if the dynamic ow of control
happens to go along that trace. When an instruction
is moved up past an \o -trace" edge that connects a
side trace into the current one, a copy of that instruction needs to be inserted on the o -trace edge. This
copy is refered to as compensation code.
Naive insertion of compensation code penalizes the
o -trace path in order to speed up the current trace,
because it produces sparsely scheduled cycles at the
trace join point [8]. The ideal solution is to somehow absorb the compensation code into the side trace,
without lenghening the side trace.
One way to do this is to schedule the side trace (if
it isn't already) and then replace any NOP instructions in its schedule with the compensation instructions. A variation is to allow the side trace schedule
to be lengthened only up to some threshold.
The problem is that replacing a NOP with a compensation instruction could introduce a structural hazard with something that was either issued earlier in
the schedule or something issued later in the schedule. The rst part, i.e., the detection of a structural

6 Other Uses of the Automata

The forward automaton encodes all possible legal
instruction schedules for a particular implementation
of the processor's instruction set architecture. This
suggests that the forward automaton might be a useful tool for CPU testing. Executing the sequence of
instructions corresponding to every distinct path beginning and ending at F0 in the forward automaton
will make the processor go through all the possible
pipeline state transitions and therefore exhaustively
test the chip for all possible code sequences that the
compiler can ever produce. Such a method may be less
time consuming than random testing of the pipeline
hardware.
Another example of the usefulness of the automaton
representation was demonstrated when the KSR2 processor, a revised faster-clocked version of the KSR1
processor was delivered to the KSR compiler group.
Although the two chips had the same architecture and
hardware resource usage vectors for the instruction
set, a hardware bug in the KSR2 required a compiler
workaround. There were two speci c instructions I and
J that should never be scheduled one cycle apart (i.e.,
they could be scheduled in the same cycle, or 2 or more
cycles apart, but never 1 cycle apart).
This is an arbitrary scheduling restriction, but one
that can be modeled in terms of resource usages. Our
solution was to introduce a dummy hardware resource
x. We modi ed the resource usage vectors for instructions I and J so that instruction I used resource x two
cycles after its launch cycle, and instruction J used
resource x during its launch cycle. The resulting automaton only accepted schedules in which I and J were
not separated by one cycle. What could potentially

the compiler code.

7 Conclusions

We have presented algorithms for building a forward
and reverse automaton from a table of instruction resource usage vectors for a processor implementation.
This is done once at compiler development time, and
the generated transition tables are used by the compiler's instruction scheduler each time it compiles a
program for that processor. A factoring scheme gives
the compiler architect a spectrum of space/time tradeo s for optimizing the size of the automaton transition tables. The key insight here is that the instruction scheduler really wants to reason about schedules, and not about what hardware resources are used
where. The dual automata lets us treat the instruction scheduling process as the recognition of strings in
a language.
Additionally, we also presented techniques for using
these dual automata during global instruction scheduling, to perform many powerful transformations involving already scheduled blocks. These can be implemented eciently (constant time feasability test, linear time updates), and incur substantially less space
overhead than traditional methods.
Dual forward and reverse automata have been used
for scanning regular languages [12], but we are not
aware of other work that discusses their use in global
instruction scheduling. We implemented an early version of the techniques presented in this paper in a
large (over 150,000 lines of C) production compiler
at Kendall Square Research, to generate code for the
KSR1 and KSR2 processors used in the KSR/Series
supercomputer products. In the KSR compiler implementation, the automaton table lookup replaced
about 2000 lines of C code (out of a total of 6000 lines
of instruction scheduler code) that was being used to
model all the complex restrictions of the KSR processor pipeline.
The goal of our global scheduling strategy was to
minimize the overhead due to speculative code motion
even if we gambled incorrectly on the direction of certain branches. Each block was rst locally scheduled,
and thereafter instructions from other blocks along a
likely trace were speculated up to replace NOPs in the
current block. These speculated instructions left NOP
holes in their original home blocks, which in turn were
lled in by further speculations from below. The dual
forward and reverse automata made such a strategy
eciently implementable. In fact our new improved
global instruction scheduler that did the speculative
code motions often ran faster than the old local instruction scheduler (that did not have the bene t of
using the automaton tables), and the generated code
was at least as ecient.
