-Notation in Programming Logics

Most logics for reasoning about programs rely on a pun between expressions in the programming language and terms in the logic. In logics based on the predicate calculus, this
pun breaks down for higher-order languages that use -notation because the  operator
binds free variables. In the predicate calculus, operators within terms must be ordinary
functions, which cannot bind variables. The standard solution to this problem is to interpret -expressions as abbreviations for terms constructed from functions called combinators;
every -expression can be expressed as a term constructed from the explicit apply function,
the constants S and K , and primitive functions on program data. Unfortunately, the
translation to combinator form produces an incomprehensible representation for program
expressions and mangles their syntactic structure.
This chapter explores a di erent approach to reconciling -notation with the combinatory framework imposed by the predicate calculus. In the predicate calculus language, we
can include primitive operations for constructing and manipulating environments. Then we
can interpret -expressions as combinatory terms without performing any translation. In
this formulation,  becomes a binary combinator  and every variable v becomes a unary
combinator v. This approach to interpreting -notation yields models for -calculus that
are more \detailed" than conventional models based on S and K because they respect the
syntactic structure of program expressions. In fact, we can use this approach to construct
models for the -calculus with dynamic binding and the  -calculus with variables, an extension of the -calculus that incorporates explicit substitutions, developed by Abadi, Cardelli,
Curien, and Levy [1]. The  -calculus provides a semantic justi cation for computation
strategies that defer substitutions by constructing environments.
Another motivation for interpreting  as a combinator is that it permits denotational
de nitions of programming languages to be formulated as homomorphisms from syntactic
algebras to semantic algebras. Given a term algebra S for the abstract syntax of a programming language, we can de ne its semantics as a homomorphism  from S to M, where M
is an algebra with the same signature as S. Conventional denotational de nitions do not
exhibit this property because binding operators (such as ) are interpreted as special forms
rather than operations (combinators) in a semantic algebra. Formulating denotational
de nitions as homomorphisms yields bene ts beyond mathematical elegance. It imposes

and
 functions (denoted by -expressions) can be passed as arguments to other functions
and returned as the values of function applications.

10 Comparison with FP

The homomorphic interpretation of program syntax in F may appear unorthodox, but the
same approach to semantic de nition has been widely publicized in a slightly di erent form
in the FP language created by John Backus [Backus 78]. In FP, the primitive operations
are functions on input sequences and higher-order operations for combining functions. FP
ostensibly has no variables; the program extracts elements from the input sequence using
selector functions 1, 2, : : : which extract the rst, second, : : : elements of the input sequence. However, these functions are directly analogous to the interpretation of variables
x; y; : : : in homomorphic models of the -calculus. In these models, the variables x; y; : : :
are interpreted as selector functions x; y; : : :, which extract the speci ed elds from the environment. The environment is a function mapping identi ers to values; we can concretely
represent it as a record. Hence, the only real di erence between our interpretation of free
variables and the sequence selectors of FP is that free variables extract particular elements
from records (functions mapping identi ers to values) while FP selectors extract particular
elements from sequences (functions mapping the integers f1; 2; : : :; kg into values). When
we interpret  as a combinator, FP and the -calculus are essentially the same language
adapted to di erent input data structures. FP does not permit the de nition of higherorder functions, but this is an arbitrary restriction that has been eliminated in more recent
dialects such as FP84 [8].

11 History and Related Work
While I was a graduate student, John McCarthy suggested extending the set of terms in
the predicate calculus to include -expressions by de ning an equivalence relation on terms
( -conversion) that models must respect. He called the extended terms extensional forms.
Several years later, during a visit to Stanford, John and I explored the idea of interpreting 
as a combinator to provide a semantics for extensional forms, but we did not nish working
out the technical details.
