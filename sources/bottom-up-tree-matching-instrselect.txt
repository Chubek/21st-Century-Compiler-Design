Abstract
Code generation in uences the eciency of not only the compiled program but also the
compilation process. The appearence of the many new processors has created the need of
automating the code generation phase. The instruction selection is a important component
to be poduced automatically in the code generation phase. The tools for automating the
instruction selection usually use the tree-structure to represent the intermediate representation. The algorithms to manipulate the tree structure are simple. And the powerful tree
rewriting tools can be automatically generated for transforming trees to target machine
code. Among many technologies for the aumatic generation, BURS technology produces
the fastest code generators.
But, BURS technology often require long time and much space to process a complex
machine description. Much e orts has gone to make BURS technology more attractive:
ecient in points of time and space. In this proposal, we closely inspect BURS technology
and propose a new method which may solve the problems of BURS technology.

1 Introduction
1.1 Background

Code generation phase of compiler generates the target program which can be executed on
the target machine. A compiler translates source programs written in a programming language L1 into target programs in another programming language L2 . In this paper, assume
that L2 is a machine language. In this case, the translation process is is partitioned into
several phases. Code generation is the nal one among these phases. It takes as input an
intermediate representation(IR) of the source program and produces as output an equivalent
target program [ASU86]. The code generation schemes depend on which IR code compiler
uses: Abstract machine, Trees, DAGs,...etc [Dav93]. In this paper, the tree structure is used
to represent IR code.
The instruction selection of the code generator plays an important role to generate a efcient code for CISC machines [PrF92]. Code generation involves selecting the appropriate
target language instructions, determining an evaluation order for operations and assigning registers to hold values [ASU86]. Among these issues, the instruction selection determines which
instructions can do best the computation of the program. To be concrete, instructions are
selected to minimize the size of the generated code, or to minimize the execution time. The
instruction sets of CISC chips are redundant. That is, computations may be evaluated via two
or more di erent sequences of instructions. The instruction selector must choose one among
the various computations to produce the best code. The problem of selecting instructions can
be a combinatorial task propotional to the size of input programs for a machine that has a rich
set of addressing modes [ASU86].
The increase of the variety of processors has created the need of automatically generating
the code generation phase [AGT89]. Recent progress in this automation has made the code
generator generator economically feasible and gain an acceptance in practice. Futhermore,
these schemes seem to be promising vehicles for estimating some impacts that a particular
1

architecture might have on compiled code size and its execution time. The automatic generation
schemes of code generator can be classi ed into two categories: interpretative code generation;
pattern matched code generation [GFH82].
Interpretative code generation approaches use the code for an abstract machine as the
IR code and then expand the code into the target code by a table of templates. Such code
generators are usally hand crafted. To generate a new code generator, the table of templates
must be made newly. Pattern matching code generation approaches use trees or DAGs as the
IR code. In the case of trees, code generator rewrites the IR tree by matching tree patterns for
machine instructions and then generates the corresponding machine instructions. Depending
on the choice of the tree patterns, pattern matching is performed either by parsing or tree
pattern matching techniques. The parsing techniques use SLR(1) parsing. The tree pattern
matching techniques are divided into two methods by matching methodology, namely, top-down
tree pattern matching, bottom-up tree pattern matching.
BURS(Bottom-Up Rewrite System) technology produces extremely fast code generators
with bottom-up tree pattern matching [HOD82, Cha87, BDB90, FHP93, FHP91, PrF92]. However, the code generator generator requires a lot of time and space to generate a code generator
for a CISC machine [PrF92]. In this paper, the problems of BURS technology and the general
description of tree patterns for a machine instructions to solve the problems is addressed.

1.2 Motivation

BURS technology generates automatically the code generator with bottom-up tree pattern
matching. From the eciency of the code generator, interests in code generator generator based
on BURS technology have been growing. Especially, many algorithms have been proposed for
the ecient generation of the code generator because BURS technology often requires a lot of
time and space to generate a code generator [HOD82, Cha87, BDB90, FHP93, FHP91, PrF92].
Although many algorithms have been suggested for the eciency, they have still required a lot
of time and space.
Bottom-up tree rewriting is solved by associating a state with the nodes of input tree. The
state is a set of tree patterns which could match some tree simultaneously. Ho mann proved
that there exist only nitely many states [HOD82]. Therefore, these states can be precomputed,
the table is constructed using these states for each operator, and then new states are generated.

A close inspection of BURS technique tells us that its ineciency comes from the way of
constructing the tables. Whenever one state is made newly, every n-ary(n  1) operator must
test whether the state has a pattern to be sons of the operator. If so, the operator can use
the state to generate another new state. As long as a new state exists, the construction of any
table can not be nished.
Some relations(subsume, independent) must exist between tree patterns to be simultaneously in a state. If we can nd the relations between arbitrary two patterns, all states can be
constructed easily from the set of all possible tree patterns (see Chapter 3). If we can only nd

Therefore, rst of all, we devise a formalized relations between tree patterns. The formalized

2.2.2 State Trimming

Many of the states created are nearly identical. The state-generation algorithm will run faster
if it can increase the likelihood that two created states will be identical. Two states can
often be made identical by trimming unessential nonterminals from the state. A nonterminal
is not essential (in a particular state) if it can be proven that it will never be needed to
produce a least-cost cover of any subject tree. Henry devised two techniques, \sibling", and
\demand" trimming, to identify when one \fcost1 ; rule1 g" (representing a nonterminal) can be
safely removed from a state because another \fcost2 ; rule2 g" subsumes it. Todd generalized
Henry's trimming techniques and developed triangletrimming for safely removing unessential
nonterminals from an state. Figure 2.7 shows the triangula shape and inequality.

2.3 Related works

Recently, there is a considerable amount of work in tree pattern matching algorithms and
in the generation of tables for the tree pattern matching [AGT89, BDB90, Cha87, FHP91,
FHP93, Hen84, HOD82, PeS88, Pel88, PrF92, Pro92]. This section brie y covers several code
generation systems that are based on tree pattern matching and dynamic programming. They
di er primarily in what technology they use to do tree pattern matching, and in the fact that
they do dynamic programming at compile time rather than compile-compile time [Pro92].

Using Parsing Techniques

Graham and Glanville(GG) tried to use the LR parsing techniques to generate codes
[Hen84]. A code generator can be constructed as a syntax-directed translator. It maps trees
into strings through their preorder traversal and has a left-to-right bias and a "greedy" approach to choose the biggest pattern among di erent alternatives. This prevates the optimal
code generator potentially. Under the mapping from trees to strings, the transformation rules
correspond to grammar rules: instruction fragment class symbols to non-terminals, and IR operators to terminals. This becomes the origin of the term machine grammar. The sentential
forms in the grammar correspond to the elements of the extended pattern set.
GG has been used to construct practical code generator generators, including CODEGEN.
The main advantage is to re-use a well known technology, SLR(1), in pattern matching and
rewrite rule application. The main disadvantage of GG is that it cannot guarantee optimality.
It is possible to perform an analysis at table construction time that will provide the user of
the system with information on those cases where the system will not optimally perform, and,
in some cases, to provide automatic corrections. But, in general, the user of the technique
requires some understanding of its fundamentals to write descriptions that will work properly.
Despite its limitations GG has been quite successful and has been a very in uential milestone.
Their works showed no di erence among SLR(1) and LALR(1) parsers because almost
any terminal admits reducing actions because of the general properties of machine description
grammars [Hen84].
Ganapathi and Fischer extended the grammatical approach by using an attribute grammar
to describe the instruction set of a target machine [AGT89, GaF88]. Grammar productions
specify the general form of machine instruction. On the other hand, semantic attributes and
predicates specify architectural restrictions. Attributes are also used to track multiple instruction results and instruction selection is done by attributed parsing.
12

Ganapathi and Fischer recommended the incremental development of a code generator
[AGT89, GaF88]. Initially, productions that describe the most general form of a target language
construct are listed. Later, special-case productions can be added to improve the performance
of the target code.

Top-Down Pattern Matching

This technique maps the problem of tree pattern matching into string pattern matching
by using as patterns the strings obtained when doing a preorder traversal of the tree patterns
[HOD82, AGT89]. Since this mapping is ambiguous, whenever any such string is found, its
origin in the subject tree is marked. Any node with enough marks is matched. The string
matching problem is solved using an automata that keeps at once track of all the di erent
strings [AhC75].
Aho, Ganapathi, and Tjiang created a tree manipulation language and a system called Twig
[AGT89]. Given a speci cation of tree patterns and associated costs, Twig generated a tree
automaton that will nd the least-cost cover of a subject tree. Twig adopted fast top-down
Ho mann-O'Donnell pattern matching[GaF88] in parallel with dynamic programming to nd
the least-cost cover.
The costs associated with patterns in Twig were more general than those a orded by BURS
system. Twig computed the cost of a pattern dynamically depending on semantic information
available at compile-time. This exibility further allows Twig to abort certain matches if
semantic predicates are not satis ed. Thus, the applicability of Twig's patterns was contextsensitive. BURS is not exible since all costs must be constants to allow dynamic programming
decisions.

Bottom-Up Pattern Matching

Bottom-up tree pattern matching is well-known and fastest technique{relying on a single
bottom-up tree walk with a simple table lookup at each node in a tree to do the matching
[HOD82, Cha87, Pel88, BDB90, FHP91, PrF92]. But, primitive state generation and statetransition tables for bottom-up tree pattern matching failed because the tables become too
large. The same is also true for simple Ho man-O'Donnell bottom-up matchers[HOD82] without dynamic programming.
Fortunately, many rows (and columns) of bottom-up pattern-matching transition tables
are identical [Cha87, BDB90]. To exploit this redundancy, index maps can be used to encode
much smaller tables. Index maps are vectors that map states of the automaton to representer
states for indexing a transition table. States may share a given row or column of a transition
table through a single indirection. Chase demonstrated that maps can be produced during
table generation so that no super uous work need be performed [Cha87].
Pelegri-Llopart, the originator of BURS theory, incorporated Chase's idea into a system
that added cost information for dynamic programming at table generation time [Pel88]. In
addition to recognizing that dynamic programming could be done prior to compile time, he
developed the theoretical foundation for showing that the process is theoretically feasible for
typical machine grammars. This allowed all rewrite rules that section 2.2 introduced.
13

[BDB90] simpli ed Pelegri's model by disallowing rewrite rules, and also generalized Chase's
ideas to use cost information. Henry developed optimization techniques to limit the number
of BURS states produced during table generation. With fewer states, a smaller automaton
is produced more quickly. Henry's techniques are much more aggressive than Chase's simple
index map techniques, but at the cost of increased complexity [FHP91, PrF92]. The table
builder uses space and time voraciously, even though it uses very complex algorithms designed
to minimize these resources [PrF92].
Todd generalized Henry's work [PrF92]. Todd's system was improved in generation speed.
In general, the method how to generate BURS state and state-transition tables have been improved because tables become too large. But, yet table builder uses space and time voraciously,
even though it uses very complex algorithms designed to minimize these resources [PrF92].
Burg is a program that generates quickly tree parser using BURS (Bottom-Up Rewrite
System) technology [FHP91]. It accepts a cost-augmented tree grammar and emits a C program
that discovers in linear time an optimal parse of trees in the language described by the grammar.
Burg's code generator is less exible and much faster than Twig's.

5 Conclusion
The instruction selection is an important component of a compiler [ASU86]. BURS technology
produces extremely fast code generators by performing all dynamic programming before code
generation [Cha87, BDB90, FHP91]. However, the code generator generator is slow and requires
much space [PrF92]. A close inspection of BURS technique tells us that one of its ineciency
comes from the way of constructing BURS tables. Whenever one state is made newly, every
n-ary(n  1) operator tests the state has a pattern to be the son of the operator. If so, the state
must create a new state together with all existing states. Besides, all tables for all operators
are made not individually but simultaneously. To create these states, however, many tests and
trials are time-consuming and the concurrent construction of tables requires much space.
In this paper, the relations between patterns for the ecient construction of the tables are
formalized. The formalism tells us that if the rewrite system has depth at most two then the
tables for all operators can be made one by one. Fortunately, a more ecient BURS table
generation algorithm may exist because most machine descriptions have tree rewrite systems
with depth at most 2. An algorithm in Chapter 4 is expected to improve the eciency of BURS
technology.
Although tree pattern matching is an excellent model for instruction selection, it has some
limitations. To model sharing, it is natural to adopt DAG-structured IR [PrF92, Pro92]. The
structure is also appropriate for expressing the side-e ects. These motivate the application of
proposed construction method to DAG-structured representation.
While BURS technology produces extremely fast code generators by doing all dynamic
programming before code generation, it prevents a compiler from computing an expression
with non-constants [AGT89, Pro92, FHP91]. In order to treat the computations, dynamic
programming must be delayed until compile time, hence, a proposed construction method will
be modi ed.
When a code generator is developed using the code generator generator, a machine description will be modi ed for several times [AGT89, GaF88]. For example, rules can be added
to generate three address instructions if desired. That a code generator must be newly made
from scratch whenever the machine description is modi ed is not desirable. [GaF88] developed
an incremental code generator generator that makes only an incremental modi cation in code
21

generator. Therefore, a more ecient incremental code generator generator using the proposed
formalism is considered.
