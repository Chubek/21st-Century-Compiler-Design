More recently, several efforts have been made

some convincing promise of their approaches. Basically,
they aim to tackle the problem by dealing mainly with
instruction selection, a crucial phase of code generation.
However, according to our observation, some decision
taken at the instruction selection phase to choose a
compound instruction is adversely affected by the
techniques applied later at the register allocation phase,
which usually causes detrimental impact on the code
quality at the end. Particularly in our study, we will focus
investigation on the effect of register coalescing [8]. The
goal of register coalescing is to simplify register allocation
by reducing the number of temporaries in the code. This
can be attained by, whenever possible, removing redundant
temporaries used in the operands of move (or copy)
instructions. In this process, it also helps the compiler to
discover a useless move instruction whose operands are all
assigned to the same register. Upon detecting a useless
move, the compiler can get rid of it immediately for most
normal cases such as when the code has no compound
instructions. However, complexity arises when the move
appears in the code as a member of a compound instruction.
This nullified compound instruction (NCI) with a useless
move is actually a basic instruction with only a single
operation, undermining the potential performance gains
that could be earned via the other compound instruction
which is selected instead of it during instruction selection
and is not nullified. In this work, we propose an approach
based on an iterative algorithm in which the discovery of a
useless move in a compound instruction after coalescing is
iteratively reported as a feedback to the instruction selector
in order to find an alternative compound instruction.
The paper is structured as follows. Section II first relates
our work with others’. Section III explains the instruction
selection algorithm for compound instructions that we used
in this work. Section IV discusses how this algorithm is
extended to collaborate with register coalescing, iteratively
improving the code quality. Section V shows the
experimental results and Section VI concludes.

ABSTRACT—A compound instruction, encoding several ALU or
memory operations within an instruction word, has been regarded
as an efficient way of improving performance. In the compiler for
embedded processors, the code generation algorithm for
compound instructions has been built by dealing mainly with
instruction selection which is a crucial phase of code generation.
In this paper, we propose an iterative code generation algorithm
for minimizing the detrimental impact of register coalescing that
is applied to the code with compound instructions generated
earlier from the instruction selection phase.
Keywords-compound instruction; register coalescing; nullified
compound instructions

I.

INTRODUCTION

Intellectual-property (IP) cores embedded in Systemon-a-Chip mostly suffer from severe design constraints on
performance, energy and storage. At the same time, they
are also required to be programmable in order to ensure
reusability towards different applications. To meet all these
design challenges, they are often implemented in the form
of application specific instruction-set processors (ASIPs).
The instructions of ASIP are normally compound
instructions [1], such as add-mult and shift-move, each of
which encodes more than one ALU or memory operations.
Their main advantage for embedded processor cores is code
size reduction in that several operations are packed inside
one instruction word. In addition, they are usually designed
to perform their internal operations in sequence or parallel
within one machine cycle. It is therefore more efficient to
execute one compound instruction for a set of operations
than to separately execute multiple instructions for them
since we can avoid the extra sequencing overhead needed
for multi-cycle instructions. Therefore, if compound
instructions are fully utilized, the running time reduction
must be substantial.
However, such advantages of compound instructions
come with a downside: they complicate the compiler’s code
generation. Recognizing parallel operations on Intermediate
Representation (IR) for a compound instruction is in fact
tantamount to solving a general pattern matching problem
on graphs, which is of NP-complete complexity [3]. This
indicates that even with a modest number of compound
instructions added, the compilation time will increase
drastically so that even after a long exhaustive search, the
compiler may not find an optimal code. Since many
embedded processors are heavily armed with compound
instructions, their code quality produced by conventional
tree parsing [6] has been less than acceptable, and thus it

RELATED WORK AND MOTIVATION

Like others for NP-hard problems, the existing
techniques for compound instruction selection, noted in the
previous sections seek to attack the problem either by using
fast algorithms for approximate solutions, or by resorting to

513

expensive ones for better solutions. In [4], Leupers solves
this problem by integer linear programming (ILP).
Although the ILP-based algorithm may run up to
exponential time, this approach exhibits good performance
increase for several kernel codes. In [5], Leupers, et al. try
to solve a similar problem with a different, yet still
expensive algorithm based on constraint logic
programming. They also demonstrate that their algorithm
can generate optimal code from data flow graphs. However,
the goal of these two approaches is somewhat different
from ours since both target SIMD-style compound
instructions. We consider a SIMD instruction to be a
limited form of compound instructions in that it is just a
collection of parallel homogeneous operations while
general compound instructions which we target here allow
heterogeneous operations inside.
The techniques for general compound instruction
selection can be found in [3], [2] and [12]. In the first work,
they took an ILP-based approach, so again their technique
is expensive as the ones listed above. In an effort to
alleviate the time complexity of other techniques,
Scharwaechter, et al. proposed a more practical approach
[2]. In their work, they solve an optimization problem of
generating compound instructions with parallel operations,
called the multi-output instructions (MOIs). Although this
is an NP-hard problem, they circumvent the complexity
with a polynomial time algorithm based on a heuristic [9],
and successfully compute approximated solutions. Despite
such approximation of optimal solutions, they claim to
acquire quite encouraging results in an experiment with
various benchmarks. Dietmar et. al. proposed a similar
approach for the near optimal instruction selection on a
graph, which is based on Partitioned Boolean Quadratic
Problem (PBQP) [12]. In some special cases including
pre/post increment addressing modes, div-mod instructions
and SIMD extensions frequently found in embedded
systems, they show a good performance increase in several
benchmark codes.

COMPOUND INSTRUCTION SELECTION

For the generation of the compound instruction in our
compiler, we choose the algorithm in [2] and implement it
in our compiler. The major advantage of the algorithm in [2]
over the ILP-based algorithms is its fast polynomial time
complexity. This advantage in fact has been pivotal for our
iterative compilation infrastructure because if the
exponential time algorithm should be used for instruction
selection, the compilation time would increase so
enormously while iterating between instruction selection
and register allocation until NCIs are all cleared.
At the core of the compound instruction selection
algorithm, there is a code generator-generator, called cburg,
which automatically builds a code generator from a target
processor description written in a tree grammar. cburg
produces a code generator that can allow the user to express
MOIs as well as other ordinary instructions. Basically it
produces a code generator which uses the conventional tree
parsing and the dynamic programming strategy for
instruction selection. First, it begins with the labeling phase:

The build code gen (BCG) phase stores all the rules
including split rules into the newly built instruction selector.
At this phase, the information is collected about which split
rules can be correctly grouped to form a complex rule. Next
in the code generation stage, the candidate set selection
(CSS) phase first identifies a cluster of nodes in a forest of
IR trees corresponding to a single basic block, called a
compound instruction candidate (CIC), which has a
member-wise match to a valid set of split rules forming a
complex rule. For example, given the forest of IR trees in
Figure 2(b), the cluster B comprising tree nodes 1 and 4 in
Figure 2(c) can be a CIC because these two member nodes
are matched respectively to the rules r41 and r42 split from
the complex rule r4. Likewise, D, E, F and G are CICs. On
the other hand, the rules A, C and H are removed from the
candidate list since their nodes in each cluster cannot be
executed in parallel due to the data dependences between
them.
The CICs computed above will be used to cover the IR
trees later at the precover and cover phases shown in Figure
1, and finally at the emit code phase, emitted into the output
code as their corresponding MOIs (i.e., compound
instructions with parallel operations). But due to some
interference imposed among them, not all CICs will be
selected for being considered in the covering phase. For
instance, although the five CICs are computed in Figure
2(c), we cannot select B and D simultaneously because
otherwise the tree node 1 in Figure 2(b) will be wrongly
covered twice. From this example, we glean a fact that we
have to select CICs carefully for a valid covering in a way
that none of the selected ones interfere each other in the
covering.
To refine the work in [2] for a more formal approach,
we have modeled the interference constraints via a
candidate interference graph (CIG), where we classify the
interference into two types and handle them properly
according to their types in the CIC selection. A node n in
the graph stands for a CIC, and an edge for the interference
between its adjacent nodes, enforcing only one of the nodes
to be selected. One type of interference represented by the
edges is the covering interference, denoted by the solid

lines in Figure 2(d). This is defined to be when its adjacent
CIC nodes share the same split rule so that selecting both
would raise a conflict in the covering, as in the case
between B and D. The other is the dependence interference,
denoted by the dotted lines in Figure 2(d). This type of
interference comes to exist between two CICs if selecting
one CIC to cover IR trees brings new dependence among
the internal nodes of the other. To explain this, assume that
the CIC D is selected to cover the tree nodes 1 and 5 in
Figure 2(b). Then this selection newly introduces the data
dependence between nodes 3 and 4 of G passing through
the nodes of D. Since this dependence serializes the
execution of its internal nodes, G can be no longer selected
for a possible generation of its corresponding MOI in the
code.
In a CIG, each CIC node m is weighted. The weight,
denoted by wm, is defined by the opportunity cost Co of a
complex rule r for the compound instruction corresponding
to m:
wm = Co(r) = ∑Cs(ri) - Cc
where Cc is the cost of the compound instruction in terms
of size and latency. When ri is the i-th split rule from r, let
r′i be a simple rule representing the same instruction pattern
as ri. Then we say the two rules ri and r′i are equivalent.
Here, we define Cs(ri) to be the cost of r′i, and ∑Cs(ri) the
total cost of all the simple rules each corresponding to a
split rule from r.* For instance, we see in Figure 2(a) that
we have Cs(r41) = 1, which is equal to the cost of the

The weight wm is elaborated to quantify the net-profit
earned by generating one compound instruction
corresponding to the CIC m instead of a list of basic
instructions functionally equivalent to the instruction. In
fact, the main task of the CSS phase is to find a set of
compatible CICs with maximum profit (or equivalently,
maximum weight sum). We say two CICs are compatible if
they obey the interference constraints. In our example, we
have four sets of compatible CICs: {B,E}, {B,F}, {D,E}
and {F,G}. The two sets {D,E} and {F,G} equally have
the maximum profit (= 2). In our example, let us assume
the latter set to be selected at the CSS phase. The problem
of selecting such an optimal CIC set is the same as the
maximum weighted independent set (MWIS) problem. For
the MWIS problem, there were developed numerous
heuristic-based approximation algorithms, paving the way
to efficiently solving the optimal CIC-set selection problem.
Thus, the original problem with k CIC nodes is formulated
as an instance of the MWIS problem, and solved by a
heuristic-based technique in O(k2) time [9].

IV.

ITERATIVE CODE GENERATION

This section starts with a discussion using an example
how register coalescing nullifies the compound instructions
residing in the input code. Then, we present our code
generation infrastructure where the instruction selection
and register allocation (with coalescing) phases run
iteratively until all NCIs disappear. In accordance with this
change for iterative code generation, we have modified the
original algorithms for register coalescing in [8] as well as
for compound instruction selection in Section III.
A major factor that affects the complexity of register
allocation is the number of temporaries in the code.
Register coalescing [8] is an important optimization
technique devised to ease the complexity by removing
redundant temporaries. In the popular register allocation
algorithm [7], the interference graph (IG) is used to
represent the live range of each operand value as a node (or
a temporary). The IG visualizes with an edge the
interference of the live ranges of two temporaries. A node
in the IG is marked if it is trivially colorable, meaning that
its corresponding temporary can be assigned any register,
irrespective of the register assignments of its neighbors. It
has a significant degree if the number of its neighbors is
higher than that of the available colors/registers; otherwise
it has a low degree [8]. Only the nodes of low degree can
be trivially colored. In the graph coloring, register
coalescing merges two nodes respectively representing the
source and destination operands of a move into a new node
whose adjacent edges are the union of those adjacent to the
nodes being replaced [8]. Later when a register is assigned
to the new node, the related move instruction becomes
useless and must be eliminated. In this manner, register
coalescing helps the compiler to eliminate many redundant
moves in the code. For example in Figure 4(b) and (c), the
instruction mov on the second line is simply eliminated
after register coalescing.

The reason is obvious. Even if the CIC, say X, has its
corresponding compound instruction nullified in the first
trial, there is still a high probability that the instruction is
not nullified again as far as X is chosen with different CICs
and forms a new compatible CIC set for the next trial. This
argument is drawn from the fact that the different mixture
of CICs may produce a different result not only of covering
but also of coalescing. So, only because it causes the NCI
problem, simply eliminating X from the CIG may deprive
us of a precious chance to discover an optimal code that
could have been achieved with X taken into account. Thus,
in our work, we instead augment the CIG with additional
interference edges in order to better tackle the NCI problem.

From the example in Section III, we have found that the
policy of choosing the best compatible CIC set according to
its profit at the CSS phase increases the chance of the
chosen CIC being selected successfully as a compound
instruction, but also found that the policy does not always
guarantee the final code with minimal cost. This is because
of the NCIs resulting from register coalescing, as already
been discussed with examples. Unfortunately, whenever
different compatible CICs are chosen, the mixture or order
of instructions in the code is changed, thus altering the live
ranges of temporaries as well. This implies that the
colorability of each node in an IG can be known only after
the CIC set is fixed. We therefore argue that in theory,
unless all CIC sets are tested for possible coalescing
beforehand, there are absolutely no means to determine at
the CSS phase what choice of CIC would result in NCIs in
the final code. Based on this analysis, we have modified the
code generation algorithm, as shown in Figure 5, such that
the register allocator has a feedback path to the instruction
selector in order to inform the latter of the existence of
NCIs.

iterative code generation with the CIG refinement is given
below.
1. Let Ψ be the sets of compatible CICs computed from
the CIG G at the CSS phase.
2. Choose a CIC set ψ ∈ Ψ such that profit(ψ) ≥ profit(ϕ)
for every ϕ ∈ Ψ.
3. Evaluate the costs of all rules split from the complex
rule forψ.
4. Using these split rules along with all simple rules,
generate the code through labeling and covering.
5. Test if coalescing creates any NCI I in the code. If no
NCI is found, jump to Step 7.
6. Let X ∈ ψ be the CIC corresponding to I. If X is the
only CIC inψ, then remove X from G. Otherwise, insert
an interference edge (X,Y) into G for every Y ∈ψ, and
go to Step 1.
7. Emit the code as the final output after register allocation.
In the worst case, the number of iterations can be O(k2)
for k CIC nodes in G, since at every Step 6, either at least
one edge is added to G, or one CIC is removed from G. For
normal cases, it is further reduced to O(k) mainly because
NCIs usually no longer appear at early iterations. Note that
even the most time consuming steps, Step 1 [9] and Step 5
[8], take O(k2). Thus, we predict that the overall instruction
selection time will be O(n3) on average because k is
asymptotically linear to n (the number of nodes in IR trees),
as shown in Figure 7. Anyhow, as verified in our
experiments, we have been able to maintain the
compilation times in a reasonable time bound (O(n)) even
if we additionally handle compound instructions for code
generation. We will discuss these experimental results in
the next section.

CONCLUSION

In this work, we make an effort to develop a practical
compiler infrastructure where we can generate code
targeting processors with compound instructions. We have
modified the original infrastructure of our compiler such
that instruction selection and register allocation iterate,
properly treating the NCIs after register coalescing.
Although our algorithm takes more time than the existing
techniques which do not handle NCIs, it can produce better
quality code which can exploit compound instructions. The
code size is reduced by up to 8% within the basic blocks
having CICs as compared to the original algorithm
explained in Section III. The runtime is also reduced by up
to 12%.
