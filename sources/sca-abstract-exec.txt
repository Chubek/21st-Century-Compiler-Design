SUMMARY
Many areas of computer performance analysis require detailed traces of events that occur during
a program’s execution. Collecting traces is expensive. The additional code required to record
events greatly slows a program’s execution. In addition, the resulting trace files can grow
unmanageably large. This paper describes a technique called abstract execution that alleviates
both problems.
Abstract execution records a small set of events during the traced program’s execution. These
events serve as input to an abstract version of the program that generates a full trace by reexecuting selected portions of the original program. This process greatly reduces both the cost
of tracing the original program and the size of the trace files. The cost of regenerating a trace
is insignificant in comparison to the cost of applications that use it.
This paper also describes a system called AE that implements Abstract Execution. The paper
contains measurements that demonstrate that AE can efficiently trace large programs.

INTRODUCTION
Many areas of computer performance analysis require detailed traces of events that
occur during a program’s execution. A few obvious examples include cache memory
simulation, which requires a list of memory locations accessed by a program, performance analysis, which requires a count of each basic block’s execution frequency,2 and

ABSTRACT EXECUTION
Abstract execution is a general technique for tracing incidents during a program's
execution. Assume that we want to notice and record occurrences of a set of events E
during the execution of program P with input I (see Figure 5). Abstract execution
derives a program P' that generates the set of events E , but is simpler and faster than
directly recording all events during program P's execution. T h e set of significant events
SE recorded in the original program P drives program P'. SE should be smaller than
E , so the tracing does not disrupt the original program and the trace file is small.
This formulation allows a continuum of interpretation programs. At one extreme,
we execute an instrumented version of the original program and record events directly,
so SE contains all events in E and P' just reads this file. At the other extreme, P records
nothing and the regeneration program is an instrumented version of the original
program, so P' = P. These extremes are the approaches taken by previous tracing
systems. In general, we want a point between the extremes so the size of SE is much
less than the size of E and the cost of running P' is less than the cost of directly
measuring P.
These goals conflict. T h e principal way to reduce the size of SE is to shift computations to the regeneration program P' instead of recording values in program P. P' can
perform a computation that depends only on values that are statically determinable
from program P. Reproducing these computations increases the cost of P ' , but decreases
the size of SE.* T h e alternative is to save the result of P's computation in SE and read
the value in P'. This approach may reduce the cost of P ' , but it increases the size of
SE. In practice, the cost of P' is less important than the size of the trace file, so AE
defers computations to the regeneration program.
It might seem as if P' needs to recompute most of the original program. In fact, AE
only recalculates the instructions in the program slice for each event of interest. A
program slice with respect to an instruction I is the set of instructions in the program
that directly or indirectly affect the value produced by I.',' For example, to produce
an address trace, we are only interested in instructions that contribute to addresses
used in load or store instructions and can ignore the other instructions that produce

*However, reading a value from the trace file has a non-trivial cost, so a simple recalculation may be cheaper.

Abstract execution offers two advantages over other techniques of program tracing.
First, since SE is smaller than E , it reduces the amount of data that must be stored.
Previous systems attempted to reduce the size of files by compacting them with a data
compression algorithm. As we will see, these techniques do not reduce a trace as well
as AE and they can be applied to the SE file to increase AE’s advantage. Second,
abstract execution reduces the cost of tracing P. This reduction is valuable in its own
right if P is long-running or if tracing affects the program’s behaviour. However, it
may appear as if this reduction is illusory since the cost of P plus the cost of P‘ can be
larger than the cost of directly tracing P-ignoring system overhead required to write
larger files. AE’s advantage is that P‘ can run many times, thereby amortizing the cost
of one run of P over many uses of the data. In addition, P‘ is smaller and simpler than
the original program and uses a bounded amount of memory, so it is better suited to
being linked with a program that consumes the trace.
Abstract execution is a general technique that can record any type of event during
a program’s execution. In this discussion, we will assume that the events of interest
are the memory addresses of the executed instructions and the referenced data, in other
words, a full address trace. This is a common application of program tracing and,
because of the volume of data, a demanding test of a tracing technique. We will also
show that other types of events can easily be incorporated into the framework.

emerge, AE can be quickly ‘snapped’ into place so that it always runs in the latest

Schema generatioti and instrumentation
T h e other part of AE examines each instruction after it has passed through peephole
optimization, but before it is translated to machine code. This part produces one or
more schema instructions that describe the instruction and various annotations that
identify whether the instruction is the beginning or end of a program structure such
as a basic block or program loop. Since an R T L instruction may translate to more
than one machine instruction, AE watches the assembly code to determine the number
of uneventful-insts produced for an R T L instruction.
AE also adds assembly code to the output file to record significant events. These
sequences are written directly to the assembly output file, either immediately before
or after an instruction. Currently, there are two types of significant events. T h e first
records the number of a basic block that is the target of a conditional branch. This
quantity is typically a byte, but it can be a half word in functions containing more
than 256 blocks. T h e other type of event records the value produced by an impossible
instruction. This quantity is a full word. On a MIPS R2000, the instruction sequence
to record a significant event is six instructions for the first event in a basic block (which
checks for sufficient buffer space) and three instructions for all subsequent events in
the block. On computers without the ability to do unaligned stores (e.g. SPARC), a
full word must be stored one byte at a time.
In computers with complex instruction sets, several R T L instructions can be combined into a single machine instruction. This optimization also occurs on a smaller
scale in RISC computers in the peephole optimizer. Combining R T L instructions
causes problems if AE needs to insert tracing code between the instructions. In this
case, AE duplicates the instructions before the tracing code.
RISC computers typically require reorganization of assembly code to fill delay slots
after branches and memory loads. On MIPS computers, the assembler reorganizes the
code, and compilers are unaware of hardware peculiarities. By contrast, on SPARC
processors, gcc attempts to fill delay slots. This reorganization complicates AE since
the assembly and R T L instructions appear in different orders. However, gcc's reorganization is local and predictable, so AE can compute the relation between the two
instruction sequences.

An interesting complication is C’s setjmpAongjmp facility, which introduces nonlocal, dynamic gotos. AE follows this control flow by tracing the address of the first
argument to these functions, which is the jump buffer used to store the program’s
state, and by recording calls on these functions in the schema. T h e regeneration
program maintains a table that maps from these addresses to actual jump buffers in
the regeneration program. When the traced program executes a setjmp, the regeneration
program also executes a setjmp and associates its jump buffer with the one in the trace
program. When the traced program does a longjmp, the regeneration program uses this
table to jump to the appropriate location.
T h e interface to AE is the routine ae-recreate (file, func). file is the name of the trace
file containing the significant events. func is a function that the regeneration program
invokes on every event in the trace. func is passed two or three arguments. T h e first
is a value indicating the type of event. T h e second is the address of the event. T h e
optional third argument is auxiliary data. ae-recreate returns when the trace is completely produced.
T h e regeneration program does not dynamically allocate memory since it does not
record values. Its only memory usage is the program stack. T h e maximum depth (in
frames) of this stack is the same as the original program.
It is not necessary to profile all pieces of a program (for example system libraries).
AE produces dummy routines for all functions in the executable for which it cannot
find a schema. However, it is a serious mistake to omit the schema for a file compiled
with AE profiling, since the routines in the file produce significant events that confuse
the recreation program. Also, if untraced code invokes a traced routine, the significant
event file will be corrupted since the regeneration program cannot follow the control
flow. T h i s problem typically arises in library routines that accept a user-defined function
as an argument, for example qsort. A solution is to compile these routines along with
the rest of the program. Interrupts also cause a similar problem, but they do not have
a simple solution.
APPLICATIONS
AE has been used in several applications. One is memory-system analysis, which feeds
the sequence of memory addresses referenced by a program to a simulator that predicts
the performance of either a memory cache or virtual memory system. AE’s main
advantage in this application is the large compression of the trace file. Previously,
memory address traces were compressed by computing the difference between successively-accessed addresses-which
uncovers underlying regularity in access patternsand feeding the result to a compression program such as the Unix compress utility.4
This process typically reduces the volume of a full address trace by a factor of 10 and
an instruction trace by a factor of 200. T h e next section demonstrates that AE can
greatly exceed this compression. T h e additional compaction enables longer (and hence
more realistic) traces to be analysed, stored and exchanged.
Another application is a parallelism analyser, which examines the executions of
program loops to find the possibility of parallel overlap.> T h i s system, called pp, uses
a full address trace in addition to events that indicate the beginning, end and iteration
of a loop. pp records the last read and modification of most memory locations. I t uses

serialize a loop’s execution and necessitate delays in initiating iterations. pp computes

In this application, XE’s main advantage is again the large compression of trace files.
However, another advantage is the ease of identifying higher-level program constructs
in the trace. Some features, such as loops, can be found by analysing an assembly

Borg’s system for tracing programs on the DEC ‘Titan inspired this effort.l2 This

Independently, but slightly earlier than this work, the MPtrace system developed
some of the same ideas as AE.l3 It, like AE, does not choose the extreme alternatives
of storing a full trace or rerunning the fully-traced program to regenerate the trace. It
reduces the volume of trace data by recording control flow among superblocks (a basic
block with a single entry, but multiple exits) and by recognizing special cases of loads
and stores (e.g. a load off the frame pointer). Their system reads and modifies the
assembly code produced by the Sequent C and Fortran compilers.

memory addresses at their uses-not their definitions-and only performs local analysis

file.
T h e important difference between these systems and AE is that AE is based on a
compiler and uses a formal method to describe the distinction between tracing and
regeneration. gcc has a higher-level perspective on a program than an assembly language
post-processor and can record semantic information, such as the type of statement
making a memory reference, that is unavailable to these programs. Schemas provide
an economical way to convey static information to the regeneration program. This
information expands the semantic information produced by the regeneration program
and permits optimizations, such as using block numbers instead of addresses.
