Abstract
In the past few years a large body of work has developed on the use of typed intermediate
languages in compilers. It has become apparent that the retention of type information in
the intermediate representation of a program is useful for ensuring compiler correctness and
facilitating optimizations. The use of intermediate languages resembling typed -calculus in
the compilation of functional languages like ML and Haskell has been particularly successful,
but not much has been done on using this kind of intermediate format for non-functional
languages.
Meanwhile, TOOPL, TOIL and LOOM have been developed as object-oriented programming languages with static type-safety and semantic foundations rmly in mind. Encodings for the object and class constructs of these languages in -calculus are known, and
consideration of these encodings has proved fruitful in their design and implementation.
In this thesis, our intention is to exploit the work on the semantic foundations of objectoriented languages and on typed intermediate languages for compilation, in an attempt to
design a compiler for LOOM. Our translation makes use of two intermediate languages,
each based on a version of polymorphic typed -calculus and similar enough to the intermediate formats of other compilers to make the use of a previously developed back-end possible
in principle. We outline the design of our intermediate languages and the translations involved in our proposed compilation strategy, and we discuss our prototype implementation
which compiles a subset of LOOM into -calculus for subsequent interpretation.

Introduction
1.1 Background
In the Williams College honors thesis that introduced the object-oriented language TOIL
in 1993, [vG93], it was observed that many of the features of the language which were very
simply expressed in the formal semantics might be dicult to compile eciently. It was
further suggested that the range of complicated features like polymorphism included in the
language de nition should be limited as much as possible, to minimize the burden placed
upon those who were eventually to write the compiler. Nevertheless, the very next year
a Williams College senior thesis [Sch84] introduced PolyTOIL, which extended TOIL with
explicit parametric polymorphism. Three years later, PolyTOIL became LOOM with the
thesis [Pet96], in which a module system was added to facilitate the writing of large programs. LOOM did also simplify PolyTOIL by eliminating subtyping and relying only on
matching, but by this time it was too late to stop the expansion. The minimalist functional
language TOOPL, originally little more than a convenient shorthand for a denotational
model of objects and classes, had evolved into an imperative language with bounded polymorphism, hidden mutable instance variables, self types and a full-blown module system.
The growth and development of the LOOM family of languages has been remarkably
fruitful and instructive. Several important safety and decidability results have been proven
about the languages, and many insights into dicult language design problems have been
gained through continued work with the object-oriented type systems. But in many respects,
the progress of research focusing on these languages has been hindered by the lack of a
compiler. The interpreters that were implemented in the course of this research, while they
did provide constructive proof of the tractability of the type-checking problems and insight
by experience into the underlying semantics, were not useful for running large programs.
As the focus of the work on LOOM moved toward module systems and programming in
the large, it became more and more clear that the slow and clumsy execution provided by

an interpreter written in Standard ML would no longer be sucient. In order to justify any
claims about the convenience of new language constructs in practice, or about modularity
or separate compilation, a compiler was needed. But the problem observed by van Gent in
1993 remained: how could a compiler be constructed for such a complicated, and quickly
evolving, family of languages?
In this thesis, we will argue that the solution is to exploit the work that has been done
on the semantic foundations of LOOM and its predecessors. We will outline a compilation
strategy for LOOM that makes use of typed intermediate representations based on polymorphic -calculus. Because of the tight relationship between the semantics of LOOM
and the known encodings of objects in such a theoretical framework, translation of LOOM
programs into a typed functional intermediate language proves to be remarkably simple
compared to the task of directly generating machine code for the complex constructs of the
language. We will also discuss related work on typed intermediate languages, and argue
that the eciency penalties paid for translation of imperative programs into a functional
intermediate representation are not as large as they seem. Rather, we claim that recent
research on compilation of functional languages shows that signi cant optimizations can be
performed on -calculus-like languages, resulting in good run-time performance. We have
implemented the initial stages of a prototype compiler for a subset of LOOM, based on
the translations we specify in this thesis.
In the remainder of this chapter, we will describe some related work on compilation
using typed intermediate languages. In Chapter 2 we will provide a crash course on LOOM,
giving particular emphasis to those constructs which are handled by our prototype compiler.
Chapter 3 gives an overview of our compiler and describes IL, the intermediate language into
which LOOM programs are translated. In Chapter 4 we describe our other intermediate
language, SIL, and give the translation algorithm we use to translate between SIL and IL. In
Chapter 5 we give the translation of LOOM into SIL. Chapter 6 summarizes and evaluates
our results, gives some future directions for related work, and concludes.

1.2 Related Work
There has been a great deal of work done on the use of typed intermediate languages
for compilation, although most of this work has focused on functional, rather than objectoriented, source languages. In this section we will discuss two major Standard ML compilers,
the TIL/ML compiler and the FLINT architecture which has been integrated into Standard
ML of New Jersey. We will also discuss other work on compilation and optimization of
functional languages using functional intermediate representations, and some work on the
type system of the Java Virtual Machine.

1.2.1 TIL

The TIL/ML compiler, developed at Carnegie Mellon and Cornell Universities, is a compiler for Standard ML that makes use of a typed intermediate language to deal with some
of the diculties that arise when compiling polymorphic functions [TMC+ 96]. In contrast
to the original Standard ML of New Jersey compiler, in which all types were dropped from
expressions after a certain stage of the compilation, TIL preserves typing information all the
way through. The reasons for doing this include the possibility of more reasonable representation choices for polymorphic code and the ability to use compile-time type information
to make garbage collection more ecient.

TIL Compilation
The rst phase of the TIL compiler is the translation of Standard ML programs into a
polymorphic, typed, functional intermediate language called ML
i or Lmli. Lmli is based
on predicative polymorphic lambda-calculus, and contains mechanisms for dealing with
polymorphism eciently, including a typecase construct that is used in places where the
program must decide at run-time how to handle a value whose type is not statically known.
The Lmli representation is then transformed into a subset of Lmli which restricts the form
of expressions by requiring all intermediate values in any computation to be named and
removing almost all nested let-expressions. Because of its simplicity, this subset (called
Bform) is more amenable to optimization. After this translation has been performed, the
Bform code undergoes various optimizations including dead-code elimination, uncurrying,
inlining, constant folding and the elimination of redundant comparisions and switches. The
optimizations are applied iteratively several times, and then closure conversion (which we
will discuss shortly) is performed.
After escaping functions have been converted to explicit closures, the program is translated into an untyped language. Polymorphic functions and typecase expressions are converted into term-level functions and switch expressions, and types become terms containing
representation information. This information is used at run-time to inform the garbage collector of what kind of data is being stored in any particular variable. The untyped code is
then translated into an assembly-language-like representation, after which register allocation is performed and actual assembly code is produced.

Typed Closure Conversion
Closure conversion is the method employed by ML compilers to translate higher-order functions into a form that can be eciently compiled and executed. In languages where functions
cannot be nested, or where they cannot be passed as parameters or returned as results of
other functions, it suces to represent a function at run-time just as a pointer to the start
of its code. In languages like ML, however, this is not possible since the source code for

CHAPTER 1. INTRODUCTION

4

a function may contain free variables whose locations cannot be \compiled in" because
they may change each time the enclosing block is entered. Furthermore, if a function is to
be returned from another function, it cannot count on nding the values it needs in any
stack frame, since that frame may disappear by the time the function is called. Closure
conversion modi es all nested functions that contain free variables so that they take an
extra parameter, an environment record, which will contain the values of the free variables.
Once this has been done, the function no longer depends on the context of its enclosing
block and can be hoisted to the outermost level of the program. Each time the block that
enclosed the function is entered, an environment record can be created with the appropriate
values and packed with the code pointer as a closure. Any calls to the function are then
rewritten to pass the environment parameter in addition to any user-speci ed parameters
for the function.
The early SML/NJ compilers removed all type information from a program starting
at the closure-conversion stage [AM87, AM91, App92]; the designers of TIL wanted to
avoid this, but there were some complications to proper representation of closures in a
typed language, particularly in the presence of polymorphism. The report [MMH95] gives
a detailed account of typed closure conversion. In both the monomorphic and polymorphic
cases, the process is considered as two stages: the rst, abstract closure conversion, takes a
program in a lambda-calculus-like source language and converts it into a format in which
the operation of creating a closure from the code of a function is explicitly represented. The
second stage, closure representation, translates this result into a language without explicit
closures, where no functions have free variables. Closures are represented as pairs containing
a closed lambda expression (possibly represented in the eventual machine language program
as a pointer to the code of the function) and an environment value, which is usually a record
whose type depends on what variables appeared free in the original function. To make this
translation preserve type soundness, this nal target language incorporates existential types,
which are used in the representation of closures so that di erent functions may use di erent
environment types but the types of closures for any functions of the same type in the source
language will coincide.
The polymorphic case is similar, but it is complicated by the fact that any function
code may contain free type variables as well as free term variables. This is dealt with
by packing a \type environment" with each closure, the kind of which is hidden using a
higher-order existential. Unfortunately, hiding all of this type information is not necessarily
what is desired, since the type of the function being represented may itself depend on one
of the free type variables. To x this, Minamide et. al. are forced to use translucent
(or \manifest") existential types, so that the information necessary to make uses of the
closure well-typed is revealed. Crary, Weirich and Morrisett [CWM98] argue that this is
only a problem because of the dynamic type-passing semantics of TIL. In a type-erasure
semantics, closure conversion need not be performed for type variables since application of
a polymorphic function to a type will have no run-time e ects. This fact is also exploited

in [MWCG97], which we discuss later.

1.2.2 FLINT

The more recent versions of Standard ML of New Jersey have been modi ed to replace the
original intermediate representation with a new, fully typed intermediate language called
FLINT [Sha97a, Sha97b]. Like TIL, the FLINT language is based on predicative polymorphic lambda-calculus. The designers of FLINT, however, present their intermediate format
as part of a compiler architecture suitable for compiling any higher-order typed language,
including domain-speci c application languages and object-oriented languages such as Java
in addition to ML and its close relatives [Sha97b]. It is argued that the existence of a universal compiler architecture would improve the interoperability of di erent programming
languages and the portability of programs from one hardware architecture to another. The
idea behind the FLINT architecture, then, is to allow front-ends for di erent languages |
ML, Java, Haskell, and so on | to translate their source programs into the FLINT intermediate format, and provide a middle-end optimizer and several back-end code generators
(one for each of an unlimited number of target architectures). All these parts are intended
to be completely modular, making it a simple matter to retarget a compiler to whatever
platform is desired, and a single compilation manager could be used to control the compilation of programs with components written in several di erent languages. While SML/NJ
is the only compiler so far to adopt FLINT, front-ends for other languages (notably Java)
are being developed actively by the FLINT group.
The core FLINT language is a straightforward, predicative, higher-order lambda calculus. The full language augments the core with several primitive type constructors such as
exceptions, sum types, ML-style recursive datatypes and more. Since FLINT is intended to
be useful for all kinds of programming languages and applications, many practical primitive
types and constructors are included, including di erent sizes of integers and oating-point
values, mutable reference cells, arrays, vectors, rst-class continuations and suspensions for
lazy evaluation.

1.2.3 Other Functional Language Compilers

The Church Project has developed a typed intermediate language that integrates controlow information into the representation of a program [DMTW97]. All arrow types in the
language, which is presented as a tool for compiling ML, are annotated with source and
sink labels corresponding to all the places (lambdas) where a value of that type might
have come from and all the places (application sites) where it might be applied to a value.
Each lambda and each function application site in a program is given a unique label to be
used for this purpose. The language also contains \virtual" union and intersection types,
which function like the conventional sum and product types except that these new types

CHAPTER 1. INTRODUCTION

6

are intended to have no run-time signi cance. Rather, they are a notation used by the
compiler to keep track of the di erent possible sources and sinks for a functional value and
generate the proper code to deal with function calls as eciently as possible. Some, but
not necessarily all, of the virtual tuples and virtual variants in a program may be converted
to actual tuples or variants in later stages of the compilation. [DMTW97] gives a detailed
account of the several steps involved in translating and optimizing a program using this
ow-annotated typed language.
There has also been work on transformation-based optimization of intermediate code in
Haskell programs. [Pey98] describes the optimizations performed by the Glasgow Haskell
Compiler, all of which are implemented as transformations on the intermediate representation of programs. The optimizations include avoiding the creation of a thunk to suspend a
computation that will certainly be performed anyway, rearranging case statements so that
alternatives which will never be executed can be thrown away, explicit boxing and unboxing
of numeric values, and many others. A compiler for a lazy language such as Haskell has a
fair amount of freedom in moving code around, since hardly anything has any side-e ects
and the programmer is not expected to care in what order expressions are evaluated. The
Glasgow Haskell Compiler, therefore, has many \code motion" transformations that oat
chunks of code around in an attempt to minimize the number of times an expression must
be evaluated, the size of the thunk allocated for a computation, and so forth. While the
lazy evaluation semantics of Haskell makes the optimization segment of a compiler for that
language very di erent from that of an ML compiler, it has also been argued [PLST98] that
this is needless and that in fact a common intermediate language can be used for both.
A slightly di erent approach has been taken to compilation of functional languages by
type-soundness-preserving transformations of polymorphic languages in [MWCG97]. In that
paper, Morrisett et. al. give a formal de nition and correctness proof of a transformation
from polymorphic lambda-calculus (System F) to a low-level typed language similar to
the assembly language of a RISC architecture. The compilation is simply the composition
of conversion to continuation-passing style (for more on CPS see also [App92]), closure
conversion, hoisting of lambda-expressions to the outermost level, introduction of explicit
heap allocation and nally code generation. Because of the nearly imperative style of the
closure-converted, continuation passing representation of the program, the code generation
is not very complicated. The type-preserving properties and operational correctness of all
the steps in this translation are proven. The code written in continuation-passing style does
not make explicit use of a stack for activation records; it is possible, however, to force a
stack-based discipline upon the code by changing the way in which continuation values are
handled [MCGW98].

1.2.4 The Java Virtual Machine Language

The language Java [AG96] is compiled, not into native machine code, but into a bytecode
format known as JVML [LY97]. While JVML is not really an intermediate language |
nothing comes after it in the compilation process | it is worthy of some attention. In order
to make interpretation of compiled Java programs ecient and safe, the JVM bytecode
format contains information about the types of variables. Before the code of a class is
executed, it must pass the bytecode veri er, the job of which is to ensure that the bytecode
is legal and that the types of objects and other values are respected. While this is bene cial
in terms of the security issues inherent in the internet-based deployment of Java programs
and of the eciency with which they can be executed once loaded, there are some problems
from our point of view. The rst is that the type system of JVML very closely mirrors
that of Java itself: classes function as the types of objects, all subtypes must be declared as
such, method types may never change in subclasses, and there is no polymorphism. These
restrictions would make it dicult to use JVML as a target or an intermediate language
for more exible languages like LOOM. In fact, all the work of Burstein [Bur98] and the
implementors of other extensions of Java would have to be repeated for LOOM, resulting
in a clumsy translation producing inecient code.
The second reason JVML is not useful for us is that it is dicult to reason about. In
particular, the dynamic linking and loading necessary to the uses for which JVML was
designed make its type system and semantics very complicated. The ability of one class in
a Java program to be rewritten without recompiling other classes that depend on it brings
up complex questions of binary compatibility [DWE98]. There are also diculties having
to do with verifying simple method bodies: the rules necessary for guaranteeing that newlycreated objects are always initialized before any messages are sent to them [FM98] and
that exception handlers do not get confused about the types of local variables or operand
stack contents [SA98] are quite complicated, and the standards built into the original JVM
veri er are in many cases not strong enough to guarantee safety of Java programs.

1.2.5 Summary

There is a large body of work on the compilation of functional languages, and in particular
on the use of typed intermediate languages based on lambda-calculus. Transformations
from lambda-calculus to assembly language have been de ned rigorously and proven correct. Most of the work on compiling useful source languages has focused on functional languages, notably Standard ML, and in particular two full-scale optimizing compilers, TIL and
FLINT, for SML have been produced. Both use a predicative polymorphic lambda-calculus
as the core of their intermediate languages. TIL is solely an ML compiler, while FLINT
is intended as a universal compiler architecture that can be used to construct productionquality compilers for any higher-order typed language, including object-oriented languages.

Extensive use of a typed intermediate language is also made by the Glasgow Haskell Compiler, and it has been suggested that Haskell and ML compilers might even be able to share
a common intermediate language. Finally, we have seen that while the Java Virtual Machine does provide a possibly useful partially-compiled format for object-oriented languages,
the JVM is too restrictive and not well enough understood for our purposes in compiling
LOOM.

Features of LOOM
In this chapter, we will give a description of the features of the LOOM language, focusing
primarily on those which have been implemented in the prototype compiler. For more
details on LOOM we refer the reader to the papers [BFP97] and [BFSvG95] and the thesis
[Pet96].

2.1 Program Organization and Control Structures

LOOM is an imperative language, and so most of the work in a LOOM program is done in

lists of statements, which are written separated by semicolons as in Pascal. The most basic
LOOM statements are the assignment and the procedure call; more complex statements
are formed by grouping statement lists with the control structures if, while and for. An
abbreviated grammar for LOOM statements is given in Figure 2.1.
The overall layout of a LOOM program is very Pascal-like. Declarations and statements
are arranged into blocks, where a block consists of a list of constant de nitions, a list of
variable de nitions, and a statement list. Each procedure, function and method de ned in
a program can have a complete block, including its own constant list. Functions and classes
are rst-class values in LOOM, so they can be (and usually are) de ned in the constant
section of a block; this means that procedures, functions and methods can de ne their own
local subprograms which are visible only within the scope where their de nitions appear.
In addition, the last statement in any block used to de ne a function must be a return
statement which speci es the value the function should return. The return statement
may not appear anywhere else in any statement list, and LOOM does not provide a way to

2.2 Objects

Most of the interesting features of LOOM are to be found in the way it handles objects.
Since the precise de nitions of the nature and origin of objects vary from one object-oriented
language to the next, this section will explain the meanings of the important object-oriented
terminology as it pertains to LOOM. Section 2.3 will describe the speci cation and creation
of objects in LOOM, and those following will discuss some of the more advanced features
of the language.
A LOOM object should be thought of as consisting of two parts: its state, which is
represented by a collection of mutable instance variables, and its methods. Methods are
procedures and functions associated with an object; their bodies may refer to the mutable
instance variables but in all other respects they are xed for the lifetime of the object.

Unlike many other object-oriented languages, notably Java [AG96] and C++ [ES90], which
allow instance variables to be declared \public," LOOM restricts access to all instance
variables to within method bodies, e ectively declaring all of them \protected." Thus the
visible part of an object in any scope other than a method block is just its collection of
methods; in LOOM this view is captured by the object's type.1 As the example in Figure

where a method signature is an identi er (the method's name) and a type expression (the
method's type), which must be a procedure or function type.
In the example, an object type called Point is de ned; this might be the type of an object
used to store the coordinates of a point on the display in a graphics application. The object
type does not allow us to see what type of data is used to represent this information, and so
we can only interact with the object through the interface provided by its methods. In the
case of the Point type, we are provided with getX and getY methods, which presumably
return the x and y coordinates of the point, respectively, a norm method which returns
the point's distance from the origin (0; 0), and nally a moveTo method which changes the
point's internal state so that it represents the new location whose coordinates we specify.
Insofar as an object type speci es only the names and types of methods, omitting any
information about instance variables or the way methods are implemented, it is similar
to an \interface" in Java. Unlike Java, however, LOOM determines equality of types
structurally rather than by name. Thus, for example, if the de nition in Figure 2.3 were
repeated and given a di erent name (say Point2) then the types Point and Point2 would
be interchangeable.
The example in Figure 2.3 also de nes a procedure called transPoint that accepts a

common to many object-oriented languages, for invoking a method of the object p. The act
of calling an object method is traditionally known as message-sending, since by calling the
method we are in e ect \asking" the object for some information or to perform some action.
LOOM actually treats message sends a little di erently from many languages in that the
expression p.getX() is interpreted as \call the function p.getX with the empty parameter
list," which means that p.getX is just the description of a function. This function { the
method that has been \extracted" from the object { can be passed around just like any
other value, and it will continue to refer to the same object p from which it was taken.

2.4 Inheritance and Matching
Inheritance is a concept fundamental to object-oriented programming. The basic idea is
to promote code re-use by allowing the programmer to use a class she has already written
to derive another class, called a subclass, that is largely the same. When creating a new
class in this way, all the programmer has to do is give the changes between the old class
and the new one. Only certain kinds of changes are permissible: new instance variables
and methods may be added, existing methods may be rede ned by giving a new body to
replace the old one, and the initial values of existing instance variables may be changed.
Even with these restrictions on how a class can be modi ed when deriving a subclass, major
complications are introduced into the type-checking of the language by the fact that method
bodies written for one class may end up being used in another. As a result, the rules for
type-checking all classes must take the possibility of inheritance into account.
An example of inheritance is given in Figure 2.5, which shows a new class, called
ColorPointClass, being derived from the PointClass class of the previous section. A
third class, SpecialPointClass, is then derived from ColorPointClass. Both of these
classes generate objects of the type ColorPoint de ned at the start of the code fragment,
but objects produced by SpecialPointClass always start out as blue points at the origin
and color themselves red every time they are moved.
As the gure illustrates, the de nition of a class derived by inheritance looks very much
like a normal class de nition, except that the superclass { the class from which a subclass
is being derived { is speci ed using the inherit keyword. If the superclass expects any
parameters, their values must be speci ed; these values may come from the subclass' own
parameters, as in ColorPointClass, or they may be constants as in SpecialPointClass or
any other expressions of the proper types. If the new subclass is to have any new instance
variables in addition to the ones being inherited from the superclass, these are speci ed in
a var section; if there are to be any new method de nitions, these go in a methods section
just like in a regular class de nition. Note that because SpecialPointClass rede nes the
moveTo method { that is, overrides it by providing a new implementation { it must include
the clause modifying moveTo in its header. This language feature protects the programmer
from accidentally rede ning a method he didn't know was in the superclass.

instance variables and methods of the class, even those inherited automatically from the
superclass, are visible.3 Also, if a method that is inherited unchanged ever calls a method

intuitive and convenient for the programmer, we will see in later chapters that it complicates

object that has at least all the methods with all the same signatures as the class in which
that method body resides. However, she cannot correctly infer that self is an object of
the type generated by the class she is writing: the method that refers to self might be
inherited by, and executed on behalf of, another class that adds some new methods. It is,
therefore, impossible to statically know the exact type of any occurrence of self. To deal
with this problem, LOOM gives a special name, MyType, to the type of self, and the
programmer can use MyType as the type of any instance variable, method parameter, or
method return value in the class. To prevent the programmer from writing any code that
might lead to type errors when methods are inherited, the LOOM type-checker enforces
the restriction that any operations performed on self or any other value of type MyType
must not assume any more about the type than that it has at least the methods of the class
in which the occurrence appears.

determine by inspection that an object generated by ColorPointClass will have exactly the
same methods as an object of type Point, plus the new methods getcolor and setcolor.

explicitly { we could have de ned it that way to begin with, but the include shorthand
makes our intentions clearer and additionally reduces the amount of changes we must make
if we wish add a new method to Point.
It is clear that the objects generated by any class de ned using inheritance will have
all the same methods as objects from the superclass, and possibly more. We express this
by saying that the type of the subclass objects matches that of the superclass objects; in
general one object type T1 matches another object type T2, written T1 <# T2, if T1 has all
the same methods, with all the same signatures, as T2, plus possibly more. This is similar
to the notion of subtyping that is present in many object-oriented languages, but there is an
important di erence. In Java, C++ and Ei el one is allowed to use objects of a subclass as
though they were elements of a superclass: that is, assign them to variables declared to have
the superclass type, pass them as parameters to functions expecting superclass objects, and
return them from functions that are supposed to return superclass objects. In LOOM this
is not allowed. The reason for this has to do with the fact that LOOM programmers are
allowed to use MyType as the type of a method parameter. It is possible to write a simple
program using MyType and this kind of \subsumption" rule in which a message ends up
being sent to an object lacking the corresponding method, resulting in a run-time error.
For more information on these type-safety issues we refer the reader to [BFP97] and [Bru97];
for the purposes of this chapter it suces to say that LOOM abandons the convenience of

2.5 More Advanced Features

The LOOM language incorporates several advanced features to allow greater exibility
in writing programs involving objects and inheritance. Some of these, like polymorphism
and the module system, are fairly standard constructs in object-oriented and ADT-style
languages. Others, like #-types and groups, are innovative typing constructs speci c to
LOOM. In this section we will give a brief overview of these features, most of which are
not implemented in our prototype compiler and will not be discussed any further in this
thesis.
The rst of LOOM's advanced features is bounded parametric polymorphism, similar to the kind found in Ei el and several proposed extensions to Java, notably Pizza
[OW97], Generic Java [BOSW97] and Rupiah [Bur98]. The idea is to allow a function
(or a method, or an entire class) to take a type as a parameter in such a way that the
type which is given \specializes" the function to act on values of that type. For example,
using parametric polymorphism one can create generic homogeneous data structures: a
programmer can write, say, a polymorphic Stack class and then specialize it as many times
as necessary to create stacks containing di erent types of values by writing Stack(Point),
Stack(OperandDescriptor), Stack(ActivationRecd), and so forth. LOOM permits procedures, functions, methods and classes to be polymorphic, and also provides a convenient
\type function" notation for describing the types of objects produced by a polymorphic
class. Our prototype compiler does not handle polymorphism, but we do intend to add
support for it in the near future, and so our discussion of the translation of LOOM will
show how polymorphic functions may be translated.
Another construct provided by LOOM that is related to polymorphism is #-types,
pronounced \hash types". Brie y, if a program has de ned Point to be an object type,
then by de nition #Point is a type containing all objects of type Point and all objects of
any type whose type matches Point. Thus, if a variable is declared to have type #Point,
then objects from any of the classes in Figure 2.5 may be assigned to that variable. This
\uni cation" of all the types matching a given type is similar to the subtyping behavior
exhibited by other object-oriented languages. In fact, the extension to Java proposed in
[Bur98] introduces \exact types" which work like normal object types in LOOM, while
object types as they would normally be written in Java are treated like #-types. The only
di erence between Java's object types, which permit subtyping, and LOOM's #-types, has
to do with MyType. While most operations on objects of #-types are the same as for exact
object types, it is forbidden to invoke a method of such an object if MyType occurs as the
type of a parameter to the method. A more detailed discussion of the reasons for this can
be found in [BFP97]. A translation of #-types into our intermediate languages is known,

CHAPTER 2. FEATURES OF LOOM

20

but we have chosen not to implement it at this time.
The thesis [Pet96] introduced a module system for LOOM, designed to support programming in the large. A LOOM program may consist of several compilation units, one
of which is the main program and the rest of which are speci cations and implementations
of modules. The module system of LOOM is similar to that of Modula-3 [CDG+ 88], and
supports the de nition of constants in addition to abstract types, partially revealed types
and transparent type de nitions. Each module has exactly one interface, which speci es
which of the de nitions that appear in it are to be visible to clients. The module system
was later extended [Van97] to weaken the abstraction barrier surrounding each module and
permit the extension of classes de ned inside.
Finally, a version of the statically-safe virtual types construct proposed for Java in
[BOW98] has been added to LOOM [BV99]. This construct addresses the problem of creating subclasses of mutually referential classes, where straightforward inheritance often fails
to preserve the mutual relationship of the superclasses. It is now possible in LOOM to dene a group of several object types all at once, and associate classes with that group. Then
when subclasses are de ned, all the cross-references between the types are updated, creating
a new group which preserves the mutually referential relationships present in the original
one. While these TypeGroup and ClassGroup constructs may be considered a straightforward extension of LOOM's original treatment of MyType and the matching relation, their
semantics are a bit more complicated in that they require mutually recursive types, which
we have chosen not to support in this rst attempt at a LOOM compiler.

3.1 The FLINT and TIL compilers

The typed intermediate languages that most in uenced our LOOM compiler design were
the TIL [TMC+ 96] and FLINT [Sha97a, Sha97b] compilers for Standard ML. These two
intermediate languages have much in common: each is based on a predicative version of
polymorphic -calculus, both support similar base types (integers, oating-point numbers,
etc.) and primitive type constructors (tuples, variants, functions, polymorphism), and both
force terms to be written in A-normal form [SW96] to simplify optimizations.
Both the FLINT and TIL systems follow essentially the same compilation strategy. Each
begins by parsing and typechecking the source program; this process, called elaboration, is
complicated by the fact that ML allows the programmer to declare in x operators and
change their precedences at will [AM87]. The TIL compiler borrows the front-end of the
ML Kit compiler [BRTT93] for this purpose [TMC+ 96]. The elaborated ML program is
then converted to a typed intermediate language and optimizations are performed. After
the optimization passes are nished, closure conversion is performed, followed by low-level
optimizations and nally code generation.
It has long been considered a good idea to compile programs written in a functional
language by transforming them into continuation-passing style, or CPS [App92]. In this
style, programs are rewritten so that every function takes, as an extra parameter, another
function to which it should pass its result. This extra function, called a continuation, is then
called as the last step performed by the original function body; because it is the last thing

the function has to do, it is a tail-call and can be implemented as a simple unconditional
branch. Because CPS turns function applications into jumps, it makes code look more
linear and enables conventional loop optimizations to be performed.
Neither the FLINT nor the TIL compiler actually uses continuation-passing style as
such, however. Instead, both translate the terms in their intermediate language into a
style referred to as A-normal form, which has been shown [SW96] to be equivalent to CPS
in terms of the optimizations that can be performed. Writing terms in A-normal form
essentially means naming every sub-expression of a computation using a let construct.
This has the e ect of turning free-form higher-order function applications and complicated
arithmetic expressions into linear sequences of simple operations and let-bindings, nally
either returning a single named value or making a tail call to another function. The result
is that the code looks very linear, and since most of the let-bindings in a term will be
simple operations, they can usually be compiled into simple machine-language instructions,
provided all the previously bound variables are stored in registers or convenient memory
temporaries. The only catch is that a -expression might be de ned which refers to one of
these temporary values; the task of saving old bindings is handled by performing closure
conversion as described in Section 1.2.1.

Compiler Design: A Narrative

Because of the amount of work involved in writing the optimization and code-generation
phases of any real compiler, we decided early on that the best course of action for us would be
to write our LOOM compiler as a front-end for either TIL, FLINT or some similar system.
In particular, since FLINT was originally intended to be a universal compiler architecture
usable for compiling many di erent source languages [Sha97b], we planned to implement
our LOOM compiler by writing a front-end to translate LOOM programs into FLINT,
and then using the middle- and back-ends of the FLINT compiler to do optimization and
generate code. By proceeding this way, we hoped to minimize the amount of needless labor
in the construction of our compiler, while at the same time maximizing the number of
platforms we could target and the amount of optimization we could perform.
Unfortunately, there are several impediments to our using FLINT e ectively for a
LOOM compiler. First of all, polymorphism in FLINT is predicative; that is, the type
system of the FLINT language mirrors that of SML [MTHM97] in not permitting polymorphic functions to be passed as parameters and disallowing polymorphic recursion. LOOM,
by contrast, does allow these uses of polymorphic functions, which means that a translation
of the full LOOM language would necessarily involve some inconvenient workarounds.
Of more immediate concern, however, was the fact that the type system of FLINT did
not include existential types. Existentials are an integral part of most of the well-known
encodings of objects [BCP96], where they serve to hide the types of instance variables.

CHAPTER 3. OUR INTERMEDIATE LANGUAGE IL

23

A translation from an intermediate language with existential types to FLINT could have
been implemented, but would have required more work than time allowed. Interprocedural data ow analysis would have been necessary to determine, for each object type in the
program, all the classes that could produce objects of that type and hence all the types
with which the variable in each existential could be instantiated; existential types could
then be replaced by nite ML-style datatypes, which the FLINT language does support
[Sha97b]. This labor-intensive transformation, however, proved to be unnecessary: in personal communication with the FLINT group [Sha98] we discovered that they planned to
add existential types to their intermediate language. This was motivated by their e orts
to write a Java compiler using FLINT, and they too had discovered that existentials were
necessary to encode object types. This addition to FLINT, though, was still in the planning
stages, and it was unlikely that a version supporting existentials would be available by the
time we needed to nish our work.
The recommendation of Shao was that we design our own intermediate language, as
similar to FLINT as possible, and use that language design to implement the initial stages
of our compiler. In order to be able to debug our translation, it was suggested that we
write an interpreter for this intermediate language so that we could run translated LOOM
programs without a real compiler back-end. When an appropriately extended version of the
FLINT back-end became available, a translation from our intermediate language into theirs
could be implemented to complete the compiler. We took this suggestion, and designed our
intermediate language IL to resemble FLINT in many respects, except for the addition of
features like existentials and impredicative polymorphism.
The nal obstacle to using the FLINT system to write our compiler was that our preferred encoding of classes [BV99] relied on bounded quanti cation, which was not present in
FLINT.1 To simplify the task of working around this, we designed a second language called

LOOM to the subtyping-ignorant IL language could be broken up into those parts which
dealt with LOOM's language features and those parts which dealt with the elimination of
bounded quanti cation. The translation from SIL to IL is nontrivial and is discussed in
Chapter 4; translation from LOOM to SIL is discussed in Chapter 5.

Because of the syntactic restriction forcing IL programs to be written in A-normal
form, the interpreter is able to execute terms in a fairly imperative style. The interpreter
executes each let-binding as though it were an assignment statement, fetching the values of
the variables on the right-hand side from the environment, performing whatever operation
is speci ed, updating the environment so that the variable named on the left-hand side is
bound to the resulting value, and then moving on to execute the remaining bindings with
the new environment. This recursive invocation of the evaluation function is a tail call,
so excessive stack space is not consumed when evaluating long programs. Furthermore,
although we currently use a splay tree (provided by the SML/NJ library) to store the
execution environment, it should be possible to design a better representation that allows
bindings to be inserted, and values changed, in constant time. Such an implementation
improvement would mirror the compilation strategy of treating variable bindings as though
they were assignments and storing as many values as possible in registers.
The execution phase of our interpreter does not make very much use of the type information in a program. Any values manipulated by the IL code are represented by a single
ML datatype with constructors for tuples, function closures, members of disjoint unions,
and so forth. This uniform representation makes it easier to build up values, pass them
around, and take them apart, but it does impose some costs in terms of eciency when we
must check that a given value really is of a certain kind. Naturally, we attempt to minimize
the number of places where this is necessary, but there seems to be no way around it in
the cases of primitive or library function application (the \integer addition" function must
extract the integer values from its arguments) and any other operations that need to access
the internal structure of some value, most notably tuple component extraction and function
(closure) application.
Another noteworthy aspect of our representation of values has to do with garbage collection. The original LOOM interpreter [Pet96, Van97] worked by directly simulating the
operational semantics of the language [BFP97], including the maintenance of a \store,"
or a mapping from numbers representing memory locations to their contents. Because of
that design choice and the representation of object references and pointers that it supports,
responsibility for the management of a LOOM program's memory rests completely on the
interpreter. Further, due to ever-present restrictions on the time and person-power that
could be applied to the LOOM project, no garbage collector for the interpreter was ever
implemented. In our IL interpreter, we attempt to make this problem less severe by taking
advantage of the fact that side-e ecting memory operations in IL are restricted to values of
ref types3 , which behave in exactly the same way as the ref types of Standard ML. It is

4.2 Translation to IL
This section will describe in some detail the translation that removes uses of records and
subtyping from SIL programs to produce valid IL programs. We will begin in Section 4.2.1
by discussing the ideas and previous work behind our translation, and then Section 4.2.2
we will give a more detailed and formal account of our translation algorithm.

4.2.1 Overview of the Translation

Our translation is very similar to that used in [BTCGS94]; the basic idea is as follows.
When we force a value of type  to masquerade as one of type  , we are essentially using
the fact that any object of type  \looks like" a value of type  . What this really means,
more precisely, is that for every value v of type  there is another value, v0 , of type  that v
looks like. In fact, in any context where a value of type  is expected, we can use v instead
of an object of type  because any expressions which act upon the value of type  will treat
v as though it were v0. Furthermore, in our SIL language we can actually construct v0 given
v { that is, given any object of type  we can actually build the object of type  that it
\looks like." We exploit this property to eliminate uses of subsumption: all we have to do
is nd places where values are forced to masquerade, and explicitly generate the value of
the weaker type that should be used.
A translation as simple as that would be sucient if all the types that appear anywhere in
the program were statically known. In SIL, however, this is not the case because of bounded
quanti cation. If the type of something that needs to be converted is not statically known,
it may not be possible for the compiler to generate the code to convert it without some help.
What is needed is for every bounded type variable to have associated with it some kind of
hint as to how to coerce it up to its bound. The solution, therefore, is to change bounded
polymorphic functions so that they must also accept a coercion function that can convert
values of the parameter type to values of the type by which it is bounded. For bounded
existentials, a coercion must be packed with the original value so that when the package
is opened, any values of the hidden type may be coerced up as well. This introduction of
coercion functions is the heart of the translation.
The nal thing we must make clear before giving the details of the algorithm is the way
type constructors of higher kinds are handled. Obviously, it is impossible to use conversion
functions of the same kind as are used for simple types, as it makes no sense to speak of
converting \values" of a function from types to types. Fortunately, this is not what we really
need anyway. The subtyping rules for SIL (Figure 4.2) de ne subtyping of type functions
to mean \pointwise" subtyping: thus if we know that a type operator F is bounded above
by G, then what we really need is to be able to nd coercions from F [ ] to G[ ] for any

In this chapter we give an overview of the translation our compiler performs to map a subset
of LOOM into the SIL intermediate language.

5.1 Early Stages of Compilation
For the syntactic analysis and type-checking phases of our compiler, we use a very slightly
modi ed version of the front end of the existing LOOM interpreter [Pet96, Van97]. These
segments of the compiler transform the text of one or more LOOM compilation units into
abstract syntax trees, and then check those trees for validity according to the type rules
of the language. The type-checker also decorates some parts of the syntax trees with type
information that it infers or deduces about the variables and constants in the program. It
is after this phase that our new code takes over and transforms the LOOM program into
a corresponding term in SIL.
The language represented by a LOOM syntax tree di ers from the concrete LOOM
language in a few ways. Firstly, in the internal version of the language it is illegal to assign to
any value that is not of an explicitly mutable type. Before type-checking can be performed,
therefore, it is necessary to make an extra pass over the tree to change all global variables,
local variables and instance variables into references similar to the ref's in SIL, IL or ML.
All occurrences of a variable on the right-hand side of an assignment, or as a parameter to
a procedure call or message send, must be changed to explicitly dereference the variable.
All classes with no explicit superclass are rewritten to automatically inherit from a root
class whose de nition is prepended to the program. Also, every object type in the program
is rewritten so that it includes all the public methods of the top class. Thus every object
type in any LOOM program will match the type TopType, which includes methods for
cloning an object. The clone operation, which makes a new distinct copy of an object
by replicating all of its instance variables, is a special case in LOOM, since it is dicult
47

CHAPTER 5. TRANSLATING LOOM INTO SIL

48

to write a typable clone method within the framework of our class encoding. Because
it requires such special treatment, we have not dealt with clone at all in our prototype
compiler.
Finally, the parser rewrites the de nition of any class that accepts parameters with
which to initialize objects. To simplify the semantics, classes in the core LOOM language
do not take parameters, and so if any parameterized classes appear in a LOOM program
they must be immediately translated away. This is done by wrapping the class in a function
that accepts the parameters and returns a new copy of the class pre-instantiated with the
parameter values. When a new object is to be created, the routine doing the creation
passes the parameters to this function and creates a single object from the resulting class,
then throws the class away. The appropriate rewriting of parameterized class de nitions is
performed by the parser.1
Once all the syntactic sugar in a program has been removed, it is type-checked. The
type-checker rewrites some portions of the syntax tree, adding explicit type information in
many places where the programmer was allowed to leave it out. In particular, procedures,
functions and classes declared in the const section of a block are decorated with their types,
as are the method de nitions in a class body. In order to be able to generate all the required
type annotations for the SIL representation of a program, we have found it necessary to
modify the type-checker to record some type information that was discarded in the original
LOOM type-checker. Speci cally, our treatment of objects requires the type of the target
of any assignment statement to be known, as well as the type of the receiver of any message
send and the function in any function call.

5.2.2 Translating Expressions

Most simple expressions are fairly easy to translate, as Figure 5.2 shows. We denote by

and select the appropriate method.

classes, we carefully avoided making the method suite function recursive, so this recursion
in methfun is responsible for any recursive behavior in or between the methods of an object.
There is a good reason for keeping recursion out of the class itself, and introducing it only
when an object is created. Because self-reference is not introduced until object creation
time, any method that calls another method will be sure to call the right one, even if the
method it is invoking has been overridden. The other observation about methfun is that
it does not make any direct reference to the instance variable record that has just been
created. This means that the code for methfun is the same in every instance of object
creation for a given class. In fact, it would theoretically be possible to make all objects of a
given class share the same methfun code, if that function were somehow made an integral
part of the class and passed around with the other components. We have chosen not to do
this in our prototype compiler, but it is an enhancement we are considering for the future.

The translation of a LOOM program block, containing various kinds of declarations, is

containing local type de nitions, and we will assume the parser transforms blocks with no
return value into blocks that return unit.
As the gure illustrates, a block is processed by translating each of its declarations
and de nitions, followed by its statement list, and ending with its return expression. We

de ned recursively so that it e ectively traverses the entire block, turning de nitions and
statements into let expressions as it goes. Type de nitions are processed rst, followed by
constant de nitions, variable declarations and nally the statement list. When types are

The other thing to notice about the translation of blocks is the use of the function DV

program ever contains a variable that is of a function type, our translator will generate a
default function which, when called, prints out a message complaining that an uninitialized
variable has been used and halts the program. Finally, the default value of any object type
is the nil reference of that type. Of course, in order to be able to compute DV( ) we have
to be able to expand the type  enough to determine its shape, so in fact our translation
must carry around more context information than we have been showing.

6.1 Summary
In this thesis, we have described a compilation strategy for a statically-typed object-oriented
language, LOOM. In particular, we have outlined a translation algorithm transforming an
abstract core of the LOOM language into SIL, a typed intermediate language based on F<!: ,
the higher-order polymorphic -calculus with subtyping and extended with tuples, variants,
records and several primitive types. We have also given a translation from SIL into IL, a
second typed intermediate language based on F! and similar to the intermediate languages
of other recently-developed compilers. We have discussed the type rules and semantics
of both our intermediate languages, and have claimed that our translations preserve both
type-soundness and meaning in the programs to which they are applied.
We have used these intermediate languages and translation mechanisms to implement
a partial prototype compiler for LOOM, based on the front-end (syntactic analysis and
type-checking) of the original LOOM interpreter. While we have neither discussed nor
implemented any optimizations or code generation for our compiler, we believe that the
similarity between our intermediate language IL and the intermediate languages of the
TIL and FLINT compilers will eventually allow us to create a full- edged compiler by
providing a translation from IL to one of those languages. The success of such an endeavor
would depend on the extension of the TIL or FLINT intermediate language to support
impredicative polymorphism and existential types; the FLINT group has stated [Sha98] that
they plan to add existentials in the near future. For the meantime, we have implemented
an interpreter for IL, which we can use to run partially-compiled LOOM programs and
debug our compiler. For simple programs, the execution speed of the IL interpreter on a
60

61

translated LOOM program seems comparable to that of the original LOOM interpreter.
We believe that our two-step compilation strategy using -calculus-like typed intermediate languages is appropriate for LOOM. The original ancestor of LOOM, TOOPL
[Bru93], was designed with an encoding in -calculus rmly in mind. Formal semantics for
TOOPLE, a slightly extended version, were discussed in in [BCK93]. The operational and
denotational semantics for the imperative language TOIL were given in the thesis [vG93],
and a formal description of LOOM has also been given. Finally, the type rules and semantics for an extension of LOOM were speci ed in terms of a -calculus encoding in [BV99].
Thus, we feel that the history of LOOM and its predecessors justi es the use of a compilation strategy based on its embedding in -calculus. Furthermore, F! is a suciently
powerful type system that just about any foreseeable extension to LOOM that may be
derived in the future will probably also be representable in SIL and IL. This should make
the compiler easily extensible to keep up with new revisions to the language.
While we rmly believe the use of a functional intermediate language is appropriate
for the LOOM language, it does appear to be very inecient compared to more direct
compilation strategies. In particular, the act of sending a message to an object, which in
many object-oriented language implementations is as simple as looking up a code pointer in
a method table and performing a single function call with the object as an extra parameter,
becomes very complicated when translated into a language without explicit objects. When
a LOOM program sends a message, it must unpack the object and pass the instance
variables into the method suite. The function to which the instance variable record is
passed, moreover, must pass a closure of itself into another function, which then creates
closures for all the methods of the object, packs them together into a record, and returns
them. The sender of the message then selects the single closure in which it is interested, and
invokes it { when everything is taken into account, the process is much more complicated in
the SIL version of a LOOM program than it would be if the message-send were translated
directly to machine code. Worse, if the type of the object is not statically known then the IL
version of the program will have to instantiate and apply a polymorphic coercion function.
The semantics of message sending are very complicated in our system, but it is possible
that the optimization modules of a well-designed back-end would lessen the amount of
work that must be done. For example, multiple message sends to the same object could
be coalesced to share a single copy of the method suite, so the business of creating the
record of closures would not have to be repeated every time. Furthermore, in cases where
the class of an object could be statically determined using data ow analysis, the tedious
lookup mechanism could probably be avoided altogether. Finally, clever representation
decisions concerning continuations and closure environments could reduce the need for reevaluating all the methods of an object each time a message is sent. Experimentation with
standard optimizations will likely have to wait until we can connect our compiler to a backend developed elsewhere, but there is reason to hope that a clever optimizer could greatly
reduce the ineciency of the code produced by our translation. Even if it should turn out

CHAPTER 6. CONCLUSION

62

that well-known optimizations do not have much e ect on the eciency of our code, we
believe that the eciency penalties are worth paying in exchange for the convenience of
semantics-directed compilation.

6.2 Future Work
In this section, we will discuss potential directions for future work on this compiler, the
translations underlying it, and LOOM in general.

6.2.1 Extensions to the Compiler

Since our prototype compiler only handles a subset of the LOOM language, a substantial
amount of work must still be done to expand our translation to cover the entire source
language. We have mentioned some of the unimplemented features in our discussion of the
translation, speci cally the inability to support mutual recursion of types or of constant
de nitions. There may be some complications in implementing these. In the case of types,
the SIL and IL languages lack the capacity to explicitly express mutual recursion, so an
extension of the intermediate languages will be necessary in order to compile mutually
recursive types properly. The appropriate extension is probably to allow the de nition of
sequences of types { that is, to add to the kind system of the language a \type tuple"
constructor which would stand for a group of several types. The existing Rec constructor
could then be used to create a recursive group of types. This kind of construction would
be essential if we were to attempt an implementation of the TypeGroup and ClassGroup
constructs of LOOM.
In the case of mutually recursive functions and/or classes, the problem does not lie with
SIL or IL, but with LOOM itself. The constant de nitions in a LOOM block may appear
in any order, which means that numerical, boolean or string constants may be intermixed
with functional and class constants. Furthermore, arbitrary expressions may be used as the
right-hand side of a constant binding, which means that it is not necessarily obvious until
type-checking time which constants are functions or classes and which ones are primitive
values. Since so much freedom is granted to the programmer in LOOM, but only - and
-expressions may be recursive in SIL, the task of determining how best to group a block's
constants into letrec de nitions is nontrivial. It may turn out that the best solution is to
place new restrictions on the order in which constants may be de ned in LOOM. In any
case, extension of the compiler to support mutual recursion in constants is left as future
work.
While in our presentation of the translation of LOOM into SIL we showed how polymorphic function types, expressions and applications are to be represented, this has not
actually been implemented yet in the compiler. The reason for this omission was simply

CHAPTER 6. CONCLUSION

63

that there was not enough time. Even though functions in LOOM may take multiple parameters, of which some are types and some are values [Van97], all that has to be done to
translate polymorphic functions is to separate the parameters to each LOOM function into
the type parameters and the value parameters. All the type parameters may be moved out
to the front of the list, and the entire function translated as a bounded -expression whose
body is a -expression accepting the value parameters. Polymorphic procedure and function
applications can be translated analogously; we anticipate no diculty in performing this
extension to the compiler.
There are also several aspects of LOOM's object-oriented features which we have not
addressed at all in this thesis. We believe most of them can be implemented in our compiler
by extensions to the object and class encodings. To begin with, we have ignored the fact
that any LOOM class is allowed to have \hidden" methods, which are only visible inside
the methods of the class and its descendants. Any class method is also allowed to access
the method implementations of the superclass by sending messages to the pseudovariable
super. Finally, it is possible in LOOM to compare two object references to see if they are
\equal" { that is, point to the identically same object in memory.
This last is particularly annoying to implement in SIL, since testing reference equality
is not supported at all, except for the fact that values of ref types may be compared to
see if they are the same. Furthermore, because of our coercion-based implementation of
subtyping in the translation to IL, an object may be disassembled and reassembled several
times, which means that two pointers to the same object may in fact point to separate
copies of the same instance variable references. The only way we know of to implement
equality testing in SIL and IL is to augment every object's instance variable record with an
extra member, its \identity." The existential in the object encoding could then be replaced
by a bounded existential revealing the presence of the \identity" eld, and two non-null
objects could be tested for equality by comparing their identities. In order to ensure that
we never run out of unique identities for objects, this eld could be of a ref type; this
way a unique one could be assigned to every live object, but when an object was garbagecollected the address its identity pointed to would become available once more. We have
not implemented this, but intend to do so in the future.
Another object-oriented feature of LOOM which will be tricky to encode in SIL is the
clone method of the standard global base class. The intended behavior of this method
is to create a new, separate copy of the object in which it is called, replicating all the
instance variable values. It is not possible to write this method in a type-safe way within
the LOOM language, so it must be provided as a primitive; however, we hope to be able to
implement it in SIL anyway. The tricky part is to ensure that the clone method is always
automatically updated when a class is inherited, so the version of it that is called for a given
object knows about all that object's instance variables. The design and implementation of
a clone feature for LOOM objects in SIL and IL is left as future work.
Finally, all the advanced features of LOOM discussed in Section 2.5 remain to be

CHAPTER 6. CONCLUSION

64

implemented in the compiler. These are, in particular, #-types, modules and groups. We
are con dent that the known encoding of #-types using bounded existentials will work;
the only diculty will be in dealing with (positive) occurrences of MyType in the type of a
message sent to an object of a #-type. That case will require the application of some ugly
coercions or wrapper functions. The original module system as described in [Pet96] seems
to have a straightforward encoding using bounded existentials, and the extended module
system described in [Van97] should not be too much more dicult. Lastly, TypeGroup's
and ClassGroup's are fairly well understood, and a candidate encoding for them is given in
[BV99]. We believe that this encoding will work, once it is extended to account for all the
technical considerations left out of that fairly abstract paper. Of course, the implementation
of the TypeGroup construct will rely heavily on mutual recursion between types, so these
fancy features cannot be implemented until the issues involving recursion are resolved.

6.2.2 Theorems to Prove

The formal speci cation of the translation algorithms we employ is useless unless it can be
applied to proving theorems about our compiler. In particular, we would like to prove that
our complete translation always produces a type-correct IL program given a type-correct
LOOM program, and that the computation performed by the target program is exactly
that which was intended by the source program. Since our translation is performed in two
separate stages, and a total of three di erent languages are involved, there are several parts
to this task. None of the proofs of these theorems have yet been written up, but some are
closely related to published work.
First, there are several theorems that need to be proved about the languages involved,
beginning with LOOM itself. None of the proofs for LOOM has been published as yet, but
they are similar to the corresponding ones for TOIL and PolyTOIL, which in turn are based
on the theoretical work on TOOPLE [BCM+ 93]. In particular, proofs need to be given that
the type rules of LOOM are sound with respect to the operational semantics that have been
given, and that the typability of a LOOM program is decidable { in other words, that a
sound and complete typechecking algorithm exists. Once the soundness of LOOM has been
established, we must do the same for the SIL and IL intermediate languages. This should
be a straightforward extension of the well-known proofs of soundness and decidability for
:
F! and F<
!.
Once the desired properties of all three of the type systems involved have been proven,
the next step is to show that if a LOOM program is type-correct then our translation
algorithm will map it to a type-correct IL program. Naturally, this would be accomplished
by rst showing that the LOOM-to-SIL translation preserves type soundness, and then
showing that the SIL-to-IL translation does as well. It will follow immediately that the
composition of these two mappings on programs will be type-soundness-preserving. The
proofs that the translations preserve types will probably be by straightforward, but very

CHAPTER 6. CONCLUSION

65

tedious, induction on the structure of the terms being translated. The nal step in proving
that our compiler works properly is to show that the translations preserve the \meaning" of
the terms upon which they act. This, too, would be accomplished by considering each stage
of the translation separately, but the proofs would be much more complicated than those
for type-safety. One source of diculty would be the presence of mutable variables and sidee ects in all three languages; while the paper [BTCGS94] gives a proof that a coercion-based
translation of subtyping preserves the meaning of terms, it does so for purely functional
source and target languages, so it is not clear whether that proof would be applicable to
our situation. Nevertheless, we are con dent that an appropriate proof of correctness is
possible and that our translation represents a demonstration of the applicability of typed
intermediate represenations to the compilation of object-oriented languages.

Using the LOOM Compiler
B.1 Directory Organization

All of the LOOM-related tools reside in the same directory on the Williams CS Department
system. Since it may be moved around, we'll refer to it simply as LOOM/. This directory
contains the following subdirectories:
 LOOM/src contains the source code for all the tools. It has the following subdirectories:
{ LOOM/src/LOOM contains the source code of the LOOM parser and type-checker,
including the de nitions of syntax trees.
{ LOOM/src/LOOMint contains the source code of the remaining parts of the LOOM
interpreter.
{ LOOM/src/LOOMtrans contains the code for the translation from LOOM to SIL
and the top-level module of the LOOM compiler.
{ LOOM/src/ILint contains everything pertaining to the de nition of IL, including
the syntax trees, parser, type-checker, interpreter and pretty-printer.
{ LOOM/src/SIL contains code pertaining to the de nition of SIL, including syntax
trees, parser, pretty-printer and translator into IL.
 LOOM/bin contains the heap images of the tools, as produced by SML/NJ. It also
contains one-line shell scripts for invoking each program using the SML runtime.
 LOOM/iltest contains some IL programs for testing the IL interpreter.
 LOOM/siltest contains SIL programs for testing the SIL translator.
 LOOM/loomtest contains LOOM programs for testing the LOOM compiler.

B.2 Compiling the Tools

The LOOM tools rely on the SML/NJ compilation manager; each subdirectory of LOOM/src
contains a sources.cm le which can be used to compile the corresponding application.
Also, the top-level structure of each application contains a function for creating an \executable" heap image. To automate this task, each directory also contains a le makexxx .sml
which performs the necessary steps to create an up-to-date heap image for the application
whose code resides there. So, to build the LOOM-to-SIL compiler, use the commands:
-> cd LOOM/src/LOOMtrans
-> sml < makeloomc.sml

Similarly, the SIL-to-IL translator can be built by running SML on makesilt.sml from
LOOM/src/SIL, and the IL interpreter can be built using makelili.sml in LOOM/src/ILint.

B.3 Running the Tools

If the LOOM tools have been compiled as speci ed above, then their heap images should
reside in LOOM/bin, along with some shell scripts to load them with. Each one accepts a
very simple set of command-line arguments, as we will now describe.
The LOOM compiler, loomc, is invoked as follows:
-> loomc program.loom -s output.sil
where program.loom is the source of the LOOM program to be translated, and output.sil
is the name of the le to which the SIL output should be written. To translate this SIL
version of the program into IL, use the translator called silt as follows:
-> silt silprogram.sil output.il
where output.il is the le that will receive the IL program. Finally, interpret an IL program
using the interpreter lili:
-> lili ilprogram.il
