INTRODUCTION

Semantics are typically divided into static semantics and dynamic semantics. Static semantics define
additional constraints on syntax, sometimes called context-sensitive rules, to be checked in
conjunction with syntax analysis during compilation. Dynamic semantics are how the machine
interprets the instructions of the program during execution. Therefore, the static semantics of a
language must be defined in the language specification and the dynamic semantics must be defined
by the object code generated. Of course, the ultimate goal of the static semantic specification is
to define what object code (usually in some intermediate form) is generated for each of the syntax
rules being defined [35]. We shall be concerned here with specifying dynamic semantics.
There are numerous methods for formally specifying the dynamic semantics of a programming
language, with none being unanimously supported by anyone [24]. One of the more common
approaches is to define how programs in a particular language are interpreted by an "abstract
machine." This method was first suggested by Markov [27] who described the interpretation as an
application of transformation rules to sequences of symbols [5].
One of the earliest uses of an abstract machine to describe a complete programming language
is the technique used by Landin [20-22] to define ALGOL 60 semantics. In Landin's definition
technique, programs are translated into "extended lambda-expressions," based on Church's
lambda-calculus [9], which are then interpreted by an abstract machine [5]. The extended
lambda-expressions may be thought of as a form of interpreter-oriented intermediate language for
ALGOL 60 but their use in an actual compiler was not considered.
An even more extensive definition of programming languages by means of their interpretation
by an abstract machine is the Vienna method, used to formally define PL/I at the IBM Vienna
Laboratory [25, 26]. The Vienna method is based on an abstract machine defined mathematically
by a set of states and a state transition function, similar to McCarthy's [28] definition of semantics
by means of transition functions on state vectors. A program defined by the Vienna method has
the meaning described by the state transitions of the abstract machine while interpreting the
program [5]. The interpreter for the programming language was written for the abstract machine
in a meta-language which became known as the Vienna Definition Language (VDL) [34].
Another type of formal definition of programming languages is the compiler-oriented method.
In this method, a programming language is defined by a compiler for that language. Although de
Bakker [5] suggests that this type of definition defines semantics in terms of an actual computer,
Garwick [11] discusses the concept of "machine-independent computer" which would be described
in terms of its assembly language.

In the Experimental Compiling System (ECS) [3], semantics are formalized by defining an
intermediate language (IL) for a source language S, denoted by IL/S, and for a target language
T, denoted by IL/T [14]. In the compilation of a program in S, the program is first translated into
IL/S which is then translated into IL/T and then into T. In the intermediate language, programming
language constructs are defined by a set of procedures which are mechanically analyzed to
determine semantic information. The semantics of IL are "known" to ECS. Target code is
generated by replacing the IL procedure calls with the procedures themselves, as in macro
expansion, although in some cases an actual call to an object procedure is generated instead of
expanding the procedure. This contrasts with our objective of having a single intermediate language
for a variety of source and target languages.
With respect to compilers, the dynamic semantics of a programming language are expressed
through the intermediate code generated. In this paper, an intermediate language, called L-code,
is proposed in which it is possible to express the dynamic semantics of most programming
languages. The intermediate language was developed considering the programming languages
PASCAL [16], F O R T R A N [I 7] and the non-concurrent subset of ADA* [33] specifically and other
programming languages generally. Our goal in developing an intermediate language was to design
a suitable intermediate form for use with a compiler-compiler [8] which may be used to generate
compilers for a wide variety of source and target languages.
Intermediate code is designed to be machine-independent and, therefore, in order to preserve this
machine-independence, cannot make any assumptions about such things as computational register
and memory allocation. These functions are performed during final code generation in which the
machine-independent intermediate code is translated into actual machine code. In conjunction with
the idea of dynamic semantics defining how programs are interpreted on an abstract machine, our
intermediate language will define how programs are interpreted on a stack machine (i.e. a machine
which uses a pushdown stack as its only memory). This basic idea was first suggested by Grau [12]
and is now in common use in many intermediate languages [18, 19, 29, 36].

THE I N T E R M E D I A T E L A N G U A G E
Our intermediate language is based on Grau's [12] Translator Oriented Symbolic Programming
Language, L, hence the name L-code, which was designed for use with A L G O L 60, with some
influence from the stack-based target language used in [36] with regards to some PASCAL-like
features not found in A L G O L 60 (e.g. the record data type, the selector and the case statement).
Since the target language in [36] is used only for a subset of PASCAL, the features used needed
some modification to fit into our intermediate language.
The machine interpretation of an L-code instruction proceeds by performing an initial operation
on the counter h representing the index of the top element of the pushdown stack and then
executing a set of machine instructions. Grau described his intermediate language in A L G O L 60
augmented by the two additional operations of
(1) V < - - W. V is assigned the variable name W as its value.
(2) C(V). The name of the variable which is the value of V.
Our intermediate language is described in PASCAL and avoids using actual names of variables
but rather their location in the symbol table. PASCAL functions are used to describe attributes
of identifiers such as value, address, etc.

(2) The variables I, N, S, F, T and B have been used to represent identifiers (entry in the identifier

operations act only upon data storage).
(6) There are additional checks, and instructions to make such checks, on run-time error
conditions, such as array bounds and subrange overflow, which are not shown in the table.
In contrast with Grau's intermediate language, in which counter operations were intended to be
executed in parallel with the machine action, the counter in Figure 1 is always manipulated before
the action and never after although in the looping instructions, the counter operation is conditional
in the sense that the counter is manipulated only after the loop is exited. One further contrast is
that the instruction set of this language is considerably larger than that of the original language
L which contained only twelve instructions. However, most actual machines have an extremely
large instruction set in comparison.
In addition to those differences already pointed out between the intermediate language L and
L-code is the instruction format. In L, instructions either had no operands or had at most an
identifier operand. L-code allows two operands to specify various information pertinent to the
execution of the instruction such as type mode (integer, real, etc.) or a symbol table index when
an identifier is referenced. The two operand limit has been set only because for the instruction set
described above, two operands were sufficient to describe all necessary attributes. Another related
difference concerns the concept of"generated labels". The L-code generated for a program is stored
in an array which allows jump instructions to reference the code location it is jumping to. Since
every code location is an index into the code array, there is no need for explicit generated labels.
Instead, jump instructions explicitly reference the transfer location.

Another machine dependent feature, found only in PASCAL of the three languages under
immediate consideration, is the packed data type. This data type is designed to conserve memory
in the storage of data elements and so in the allocation of packed storage, data is typically stored
in as few bits as possible. Not only is the number of bits necessary for a certain data type totally
machine dependent, but the addressability of record components is also machine dependent (i.e.
whether a record field can begin on a word, byte or bit boundary in memory). Since at the time
of intermediate code generation, storage is not yet allocated, L-code does not deal with packed
data types. Information about packed data is, however, stored in the symbol table. Therefore, when
L-code is translated into final machine code, it can be easily determined whether an L-code
instruction references a packed data type.

(1) LOAD r,m--load the contents of memory location m into register r;

(3) r: = r <op> m (r')--perform the operation denoted by <op> on the contents of register r and
memory location m (or register r') and store the result in register r.

OTHER I N T E R M E D I A T E L A N G U A G E S
With respect to the general classes of intermediate languages described in [2], L-code is most
closely related to postfix Polish notation because of the way operands are loaded onto the stack
followed by the operation being performed. The disadvantages of postfix control instructions have
been eliminated, however, by using one and two-address instructions to perform these functions.
This allows for a compromise between postfix and three-address code. An extension of the control
ftow instructions to three-address instructions can easily be made if necessary.
The advantage of three-address code over postfix code is the ease in which intermediate code
can be optimized. However, Bruno and Lassagne [7] have shown that code for stack machines can
be readily optimized if the size of the stack is bounded. It can be assumed that we have a finite
depth stack without loss of generality. A major advantage of postfix code over three-address code
is the relative ease with which postfix code can be generated compared with three address code,
particularly for expressions.
Another well-known and widely used intermediate language is P-code [18, 19,29,30], an
intermediate form used for transporting PASCAL between machines. Since P-code is also a
stack-based language, there are many similarities between it and L-code. There are, however,
several differences between the two forms in which the advantage of L-code over P-code lies.
In P-code, there are no registers and all data is stored on three pushdown stacks. A run-time
stack is used for allocating data segment and procedure activation records. There is also a stack
used in evaluating addresses and integer arithmetic and another used for evaluating real and set
arithmetic and also for packing and unpacking packed structures. L-code uses only one pushdown
stack for all computations. This is facilitated by not dealing with the machine dependencies of

L-code is designed to be translated into a more optimized machine code where P-code is perhaps
more suited for direct interpretation [18]. Both L-code and P-code allow operands of load, store
and transfer operations as part of the instruction. A significant difference in the transfer operations
of the two representations is the presence of a table with L-code to indicate whether the transfer
is generated by the compiler to process a program-control structure or is explicitly part of the
program being compiled. This type of information is needed in optimization [18].
There are no instructions for accessing record components in P-code, such as the L-code Offset
Record Field (ORF) instruction, or explicit looping instructions such as the For Index Check (FIC)
and For Index Increment (FII) in L-code. The rationale for including the ORF instruction in
L-code is to be able to represent the structure of the original program as much as possible for
optimization purposes. It is desirable in the final machine code for record fields to be accessed
directly but this transformation can be made during final code generation. The looping instructions
are included in L-code to coincide with similar instructions in various actual machine languages.
The basic difference between these instructions and explicit incremental and conditional instructions are that the loop index address, the final value and the step are kept on the pushdown
stack until the loop is complete after which they are popped off. This corresponds to using three
registers for this purpose on the N-register machine and then deallocating the registers after the
loop (unless some of the values are needed again as determined during optimization). P-code does
contain instructions to pack, unpack and test bits within a record.
Both P-code and L-code contain instructions for manipulating activation records on the run-time
stack. In L-code, these are the Activate Procedure (ACTP), Jump to Procedure (JMPP), Exit
Procedure (EXTP), Exit Function (EXTF) and Return to Higher Level (RET) instructions. An
activation record contains linkage information about the procedure and is followed by the
parameter list, if any. Function results appear on top of the stack following a function call and
this is provided for in the activation record [12]. More detailed information on P-code, including
some implementation variations, can be found in [23, 29, 30].
In their analysis of P-code for interpretation and as an intermediate language, Kornerup,
Kristensen and Madsen [18] concluded that P-code was less suited as an intermediate language than
for direct interpretation for the following reasons:
(1) The coding of some P-code instructions in machine language is extremely difficult.
(2) Some necessary declarative information is lost in P-code.
(3) P-code instructions do not resemble PASCAL program control statements leading to some
problems in optimization.
(4) P-code is designed so that storage allocation is made before intermediate code generation, thus
referencing addresses of data objects instead of tables containing information about the object
which would be useful in assigning the final address.
In [23], a program is given to translate P-code into 8080 machine code using the 8080 hardware
stack for data storage. Although the generation of actual machine code from L-code has not been
rigorously attempted, it was designed with this ultimate goal in mind. L-code instructions are
typical of actual machine instructions but at a higher level. The disadvantages of P-code are also
not present in L-code. L-code accesses declarative tables created by the compiler which contain
all necessary information about the data objects used by the program being compiled. Furthermore,
L-code instructions do describe the structure of the compiled program.
CONCLUSIONS
In [18], the following criteria are suggested for evaluating intermediate languages:
(1) Information which is necessary to generate efficient machine code for a wide variety of
machines must be represented in or accessible to the intermediate form.
(2) With minimal processing before execution (e.g. storage allocation), the intermediate code
should be efficiently interpretable.
(3) The intermediate language should contain few structured instructions such as those found in
the higher level languages.

We believe that L-code meets these criteria. While the development of a code generator from
L-code to a specific machine language has not yet been attempted, a preliminary version of an
interpreter for non-optimized L-code has been developed as part of the compiler-compiler system
in [8]. The interpreter is written in PASCAL and is now running under VAX/UNIX* at The
University of Alabama in Birmingham.
Presently L-code can completely describe such languages as PASCAL and FORTRAN. Only
a subset of ADA can be defined so far. Extensions and improvements to L-code are now being
considered so that the complete ADA language can be defined. Other approaches being taken
toward defining ADA are described in [10] and [13]. Both of these are concerned with the definition
of a virtual machine on which ADA programs can be interpreted instead of code generation for
an actual machine.
SUMMARY
An instruction set is given for an abstract machine which uses a pushdown stack as its principal
memory. The proposed instructions serve the similar purposes of (1) defining the dynamic
semantics of programming languages by describing the operations of programs on the abstract
machine and (2) describing an intermediate language to be used in compiling programming
languages into machine language.
The intermediate language, called L-code, is based on two existing stack-oriented intermediate
languages that are specifically designed for one particular programming language (ALGOL 60 and
PASCAL). However, L-code has been generalized by additionally considering F O R T R A N and a
non-concurrent subset of ADA. L-code is intended to be suitable for final machine code generation
into a variety of target machine languages. Specific examples of L-code generated for PASCAL,
FORTRAN and ADA programs are given along with equivalent IBM 360 assembly language
instructions (assuming the IBM 360 as a target machine).
With respect to the general classes of intermediate languages, L-code is most closely related to
postfix Polish notation because of the way operands are loaded onto the stack followed by the
operation being performed. The disadvantages of postfix control instructions have been eliminated,
however, by using one and two-address instructions to perform these functions. This allows for
a compromise between postfix and three-address code. A major advantage of postfix code over
three-address code is the relative ease with which postfix code can be generated compared with
three-address code, particularly for expressions.
The principle advantages of L-code over P-code, a widely used stack-based intermediate
language for PASCAL, are:
(1) P-code was designed for interpretation and not code generation into actual machine language.
L-code was designed considering both of these goals.
(2) Storage is allocated before generation of P-code instructions. Since L-code is a true intermediate language, there will be an additional step of machine language synthesis. Storage
allocation can therefore take place before target code generation.
(3) Some declarative information is lost in P-code because instructions reference addresses instead
of names. L-code instructions assume no addressing and strictly reference data by name.
(4) P-code instructions do not resemble PASCAL program control statements leading to some
problems in optimization. L-code instructions are not language specific but are designed for
particular types of high-level language statements (e.g. case, while, f o r , etc.).
