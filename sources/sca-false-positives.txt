Abstract

Static analysis tools are widely used to detect vulnerabilities in C/C++ code, yet their
effectiveness across realistic and synthetic datasets remains underexplored. This thesis systematically evaluates five prominent static analysis tools: Cppcheck, Flawfinder,
Semgrep, Clang-Tidy, and Snyk Code. The evaluation was done using two contrasting
datasets: the Juliet Test Suite, offering synthetic examples with clearly labeled vulnerabilities, and PrimeVul, providing real-world vulnerable functions paired with their corresponding patches. An evaluation system was implemented, including automated build
support across diverse open-source projects, tool output normalization, and metric-based
classification of results. Performance was assessed using many metrics, such as Precision,
Recall, F1, pair-wise comparative measures, and the Matthews Correlation Coefficient.
The results reveal that all tools perform relatively poorly on the synthetic dataset and really
poorly on the realistic dataset. This highlights the need for tool improvement and dataset
improvements, as well as the importance of dataset diversity in benchmarking static analysis tools.
Keywords: Static Analysis, Static Analysis tools, Juliet Test Suite, PrimeVul, Cybersecurity

Introduction

This master’s thesis investigates the performance of static analysis tools (SATs) based on
different underlying technologies. The work was carried out at Sectra Communications in
Linköping, Sweden. This chapter presents the problem addressed in the thesis, the motivation behind the study, and contributions to the field.

1.1

Motivation

Cybersecurity and secure development is gaining increased importance as cybercrime continues to rise. In 2024, losses in the U.S. alone exceeded $16 billion, reflecting a 33% increase
from the previous year [17]. One of the key challenges in modern software development is
balancing the need for security with the constraints of limited time and resources. While dedicating additional effort to high-risk components can help reduce vulnerabilities, the growing
demand for software makes it impractical to ensure complete security across all systems.
Manual code reviews, where no tool is used, is a common approach to enhance the security
of software. However, this can be time-consuming and requires some level of expertise to
be effective. Static analysis is another popular approach which requires less manual work.
SATs checks code without execution, identifying bugs and potential vulnerabilities early in
development. These tools are becoming increasingly popular in software development as
security demands grow, with approximately 50% of open-source projects implementing some
kind of automated analysis tool [1].
SATs use different methods to identify potential vulnerabilities [12]. Examining their
strengths and weaknesses, it is possible to create more secure programs with less effort.
Knowing when different tools and methods excel is crucial for using them effectively.
There are several approaches on how to compare and measure the performance of SATs, such
as looking at performance on synthetic data [12], running the tool on open-source projects
and afterwards labeling the results [20], or looking at one specific project [7].
This is particularly beneficial for tools based on abstract syntax trees (ASTs), which benefit from contextual information to function effectively. These comprehensive datasets can

provide the necessary code context, improving the accuracy and reliability of such tools in
practical applications.
While several prior studies have evaluated SATs on either synthetic or real-world data, none
have systematically examined tool performance across a wide range of open-source projects
using a labeled dataset. One reason for this gap is that large, labeled datasets for vulnerability
detection have only recently become available, largely driven by the growing popularity of
machine learning. Machine learning models, particularly in the domains of code analysis and
natural language processing, require extensive labeled data for training and evaluation. As a
result, the demand for such datasets has led to large efforts to curate and share high-quality,
annotated vulnerability data.
Understanding how these tools perform in realistic settings and how their performance can
be attributed to different analysis technologies is essential. Evaluating effectiveness across a
range of real-world projects enables a deeper assessment of generalizability and reliability,
offering insight into the strengths and limitations of each tool in a wider context.

1.2

Aim

This thesis aims to address a gap in current research by performing a comprehensive evaluation of SATs focusing on C/C++ code, that are based on different technologies, with a focus
on security. This comprehensive evaluation is conducted on two distinct datasets. The first
consists of synthetic data, which allows for method validation through comparison with previous studies and enables tools to be tested on identical vulnerabilities presented at varying
levels of difficulty. The second dataset comprises real-world historical data, providing insights into how the tools perform in realistic usage scenarios. A range of evaluation metrics
is calculated and used to compare tool performance across the two datasets.

1.3

Research questions

This thesis answers the following research questions:
1.1. How do static analysis tools based on different technologies perform when applied to
synthetic datasets?
1.2. How do static analysis tools based on different technologies perform when applied to
real-world projects?

1.4

Approach

This study follows a three-stage approach to answer the research questions. Initially, the
research phase identifies tools for evaluation by investigating popularity and relevant literature.
In the second stage, the tools are evaluated on two selected datasets: the Juliet Test Suite
[2] and the PrimeVul dataset [8]. Tool outputs are standardized and documented to ensure
consistent representation and reproducibility.
In the third and final stage, results from both datasets are compared using the predefined
metrics, such as F1-score or Matthews Correlation Coefficient (MCC). This evaluation highlights the strengths and weaknesses of each tool, providing insights about their performance
in different use cases.

Delimitations

This study focuses on SATs for C and C++ code. The following aspects are considered outside
the scope of this project:

Background and Related Work

This section presents the background essential for understanding the thesis and explores related work on SAT comparisons, and the role of machine learning in this field.

2.1

Background

We must first review the core concepts and techniques underlying static code analysis to
understand how SATs perform in vulnerability detection. Static analysis is defined as "The
process of evaluating a system or component based on its form, structure, content, or documentation"[16].

2.1.1

Static analysis Techniques

Static analysis techniques can be split into different categories where the hierarchy can be
found in Figure 2.1.
Static analysis techniques for vulnerability detection can initially be grouped into two categories: code similarity-based and pattern-based. Code similarity-based tools are effective at
identifying vulnerabilities caused by code cloning but tend to exhibit a high FN rate when
vulnerabilities arise from other factors [21]. One advantage of these tools is that detecting a
single instance of vulnerable code can potentially uncover similar issues in future programs.
Pattern-based techniques are further divided into rule-based and machine learning-based approaches. Rule-based methods rely on a sufficient number of examples for rules to be defined,
either manually by experts or through machine learning. In contrast, code similarity-based
approaches are restricted to detecting vulnerabilities that are identical or nearly identical to
known code clones, and are less effective when code has undergone modifications such as
deletions, insertions, or reordering of statements [22].
Rule-based techniques use predefined rules to detect vulnerabilities. These rules are manually created by human experts, but have the disadvantage that there is often a high FP rate [4,
21].

4

2.1. Background
Machine learning-based techniques are further divided into three parts, which include
vulnerability-prediction models that use process metrics such as code churn, anomaly-detection
models that look at the source code and find abnormal patterns such as strange API usage,
and pattern-recognition models that learn vulnerable code snippets directly [21].
The third overall category is called Semantic Analysis, which approach reason about a programs behaviour rather than its surface syntax. They split naturally into two principal techniques: abstract interpretation, which over-approximates all paths using mathematical abstractions and symbolic execution, which explores concrete paths with symbolic inputs.
Abstract interpretation analyses every path at once by propagating abstract values, intervals,
octagons, taint sets, etc, through the control-flow graph. Because the abstraction is conservative, the analysis terminates and scales to large projects, at the cost of possible FPs [25].
Symbolic execution replaces concrete values with symbols and generate path constraints that
an SMT solver checks for feasibility. This allows them to uncover deep, data-dependent bugs
such as buffer or integer overflows, that pattern matchers often miss [19]. Naturally, the number of paths to explore grows exponentially with program complexity, which is problematic
for large projects like the ones examined in this thesis.

2.1.2

Static analysis tools

The study evaluates five widely-used C/C++ static-analysis tools (SATs) that rely on diverse
techniques, including rule-based, pattern-based, and machine-learning-based approaches.
The tools were chosen based on three factors:
1. Relevance and popularity: tools that are widely adopted in C/C++ development.
5

2.1. Background
2. Prior research: tools that are frequently occuring in academic literature.
3. Underlying techniques: a balanced mix of rule-based, AST, and AI- solutions.
Because reliable usage statistics are hard to find for these tools, relevance and popularity were
decided from recent studies and user reports. Preference was given to tools that are actively
maintained or released within the past decade, rather than those first launched more than 15
years ago, to better reflect current projects and use-cases.
Finally, tool selection was made to include multiple underlying technologies such as rulebased, AST and AI, which makes for a more interesting and informative comparison between
different SAT technologies.
Cppcheck
Cppcheck is an open-source, rule-based analyzer focused on finding undefined behavior and
potential security vulnerabilities in the code through a comprehensive list of checks as well
as a bidirectional data flow analysis approach, allowing it to identify certain vulnerabilities
that purely path-sensitive analyzers might miss1,2 .
Flawfinder
Flawfinder uses pattern-based matching, comparing code to a database of well-known problems, such as functions with buffer overflow risks, string problems, race conditions, potential
shell dangers, or poor random number acquisitions. The benefit of using Flawfinder instead
of grep on the source code is that Flawfinder will ignore comments and insides of strings as
well as estimate a risk level depending on the parameters3 .
Semgrep
Semgrep is a subscription-based SAT that uses rule-based matching. Semgrep has 53 default
rules which were used for the study4 . Semgrep rules are easily customized and expanded by
the user5 . There are rule sets created by the Semgrep community that can be downloaded
and applied to scans6 .
Clang-Tidy
Clang-Tidy is based on the clang static analyzer, which implements path-sensitive, interprocedural analysis based on symbolic execution techniques7 . It uses an AST-based analysis,
enabling it to do cross translation unit analysis which requires the analyzed projects to be
built and a compilation database to be generated8,9 . Clang-Tidy implements the same checks
as clang static analyzer, meaning it is a Rule-based SAT. For this study, only the security-based
checks were used10 . Clang-Tidy requires a compilation database which is a file that specifies
how each translation unit is compiled within the project.

Snyk Code
Snyk offers a suite of security-focused services. The SAT evaluated in this study is Snyk Code.
For brevity, we refer to it simply as Snyk in the remainder of this work.
Snyk uses an AI-powered semantic analysis engine alongside a continuously updated, rulebased system with known Common Weakness Enumerations (CWE) and Open Web Application Security Project categories11,12 . It combines data-flow and control-flow analysis with
predefined security rules. Snyk is an AI-driven engine that operates on a subscription-based
model with limited transparency regarding its internal mechanisms. The proprietary nature
of the tool means that the exact methodologies used for vulnerability detection, rule definitions, and AI training data remain undisclosed.

Matthews Correlations Coefficient
The Matthews Correlation Coefficient (MCC) is a comprehensive metric considering all four
fundamental metrics: TP, FP, TN, and FN. Unlike other metrics, MCC includes TN, making
it particularly useful for evaluating classifiers on imbalanced datasets, such as Juliet, where
benign samples vastly outnumber vulnerable ones.
The MCC ranges from -1 (complete disagreement) to +1 (perfect prediction), with zero indicating no better than random guessing. While commonly used in machine learning, MCC
has also been applied to evaluate SATs [5, 15]. However, prior work has shown that MCC
can produce saw-tooth effects when analyzing partial derivatives over TP and TN values,
especially in uneven data distributions where the dataset contains very few vulnerabilities
compared to benign functions [30]. Despite its imperfections, MCC offers valuable insight
into tool performance when both positive and negative predictions matter.

Datasets

This study uses two complementary datasets, Juliet and PrimeVul. The datasets were selected
during a literature review, and based on scale, earlier research and availability.
The study aimed to evaluate large amounts of real-world data, and, to no surprise, there are
not many large collections of non-synthetic, real-world vulnerabilities openly available on
the Internet. To reach the scale required for this thesis and to obtain fair, reliable results, the
8

2.2. Related work
dataset had to contain known, real vulnerabilities from earlier versions of well-known opensource projects. Such datasets are scarce, but a few have emerged recently with the rise of AI
and LLMs, all created to train these models for vulnerability detection.
PrimeVul is one of these large, state-of-the-art collections: even companies such as Google use
it to evaluate their AI. Other large vulnerability datasets, such as Big-Vul [11], use automatic
vulnerability labeling which is highly inconsistent. Instead, the vulnerabilities in PrimeVul
are selected and verified by a team of security analysts, leading to more accurate labeling
compared to automatic alternatives. The PrimeVul dataset was released as recent as last year,
with updates being made continuously. Its accompanying paper has been included in wellknown conferences such as ICSE 13 , and it clearly explains the weaknesses of popular similar
datasets [8].
Because no prior SAT research has evaluated PrimeVul, the study also needed a benchmark
to confirm that the chosen techniques and methods remain consistent with earlier work. The
Juliet Test Suite meets this requirement perfectly: it is large enough for the study, openly
available, and expressly designed for static-analysis research. No other dataset offers the
same solid structure, scale, and frequent appearance in prior studies.
Juliet
Juliet, a synthetic benchmark test suite released by the National Institute of Standards and
Technology (NIST), contains thousands of short C/C++ functions in which the vulnerabilities
are deliberately planted and fully labeled with their CWE identifiers (see Section 3.1.1)[2].
PrimeVul
To add real-world complexity, PrimeVul was used, which was developed for benchmarking
machine learning models to find vulnerabilities in source code and based on open-source
projects, where each vulnerable function is matched with the commit that fixes it, for a total
of 4 659 “before-and-after” examples [8] (Section 3.1.2). The word historical data is sometimes
used instead of realistic data to describe datasets based on past vulnerabilities. Together, the
synthetic clarity of Juliet and the realism of PrimeVul provide both a clean baseline and a
practical evaluation ground.

2.1.5

MITRE CWE Top 25

The MITRE CWE Top 25 is an annual ranking of the most critical software weaknesses based
on real-world exploit data and community input14 . This list is widely used in industry and
research, highlighting the types of vulnerabilities most frequently found and exploited in
software.

Related work

The field of static analysis for vulnerability detection has been extensively studied. This section reviews prior research on the effectiveness of SATs, their evaluation on both synthetic
and real-world datasets, and the integration of machine learning in vulnerability detection.
It also identifies key gaps in the current literature.

2.2. Related work

2.2.1

SATs on Synthetic Projects

Previous research on SATs has primarily focused on synthetic datasets [10, 18]. These datasets
consist of artificially constructed code samples that contain deliberately inserted vulnerabilities. For instance, the Juliet Test Suite is fabricated to illustrate specific vulnerability patterns
with 64 000 C/C++ functions spanning 118 CWE classes [2]. Software like LAVA [9] and
STONESOUP 15 instead inject vulnerabilities into existing code, mixing synthetic vulnerable
code into realistic codebase.
Gentsch [15] extensively evaluated open-source Static Application Security Testing (SAST)
tools for detecting vulnerabilities in C code. The study used the Juliet Test Suite and benchmarked popular tools, including Clang-Tidy, Cppcheck, and Flawfinder, examining metrics
such as precision, recall, and overall accuracy. The analysis found significant variability in
tool performance based on different fault patterns.
Cohen et al. [6] describe the ideal test suite as one that satisfies three key criteria: it is similar
to real-world production software, has complete knowledge of all vulnerabilities present, and
includes diverse types of bugs in varied contexts. Juliet fulfills the latter two parts effectively.
However, Juliet’s test cases are significantly smaller and simpler than production software.
Therefore, another dataset is needed for an accurate representation of real-world complexity.

2.2.2

SATs on Real-World Projects

Although synthetic datasets enable systematic experimentation, they often lack the complexity and variability of real-world software. Several researchers have evaluated the performance of SATs in these environments. For instance, Lipp et al. [23] assessed six different
tools on known and validated Common Vulnerabilities and Exposures (CVE) and concluded
that they were relatively ineffective, the most accurate tool detecting only 53% of the vulnerabilities in their dataset, which is based on 192 vulnerabilities across 27 projects. Similarly,
Choaroenwet et al. [3] found that individual tools correctly identified vulnerabilities in approximately 52% of vulnerability-containing commits.
Pereira and Vieira [7] analyzed the Mozilla open-source project where Cppcheck and
Flawfinder were compared. The fundamental metrics were based on a file level, meaning
if any vulnerability was found in the correct file, the whole file was counted as vulnerable. Additionally, the study reports the total number of alerts each tool generates across the
project. The dataset used in this evaluation contains 2 441 known vulnerabilities, serving as
the ground truth for measuring detection performance.
Massacci and Nguyen [24] analyzed previous work on the Mozilla project, focusing on how
the choice of dataset and ground truth influences the outcome of a vulnerability detection
study. Their findings show that different datasets and ground truth can yield varying results
even when analyzing the same software project.
The study by Beller et al. [1] showed that 77% of open-source projects use some automatic
SAT, and their manual analysis shows that 59% use automatic SAT. It gives some insight into
the popularity of SATs and their popularity in open-source production pipelines.

2.2.3

Research gap

Existing evaluations of SATs fall short in two categories. First, dataset scope: Real-world
studies usually analyze a single project or a handful of repositories, while synthetic-suite
studies cover many samples but lack real-code diversity. Second, metric coverage: Many

performance.
To close this gap, our work benchmarks rule-based and machine learning-based SATs side-byside on synthetic (Juliet) and large, labeled real-world vulnerabilities (PrimeVul) and reports
a range of metrics, including MCC and pair-wise measures, to provide a balanced assessment
of tool performance.

format. The processed data is then used for classification, where findings are labeled based
on their correctness, and finally, the results are evaluated using established metrics. Figure 3.5

3.2.1

Dataset Preparation

The only preparation needed for the Juliet Test Suite was running the provided script for
building the project. Since PrimeVul was created for machine learning, the data is already
split into test, training, and validation data containing 4 704 vulnerable-benign pairs. A script
was initially run to combine the subsets into a standard, larger dataset. The script also gathers
the commit ID for the vulnerable commit, the size of the repository, and the full file path to the
vulnerable file. If any of these could not be gathered, the pair was no longer deemed relevant
since a comparison could not be run and was thus removed from the dataset. After the initial
filtering, 6 640 data points remained, resulting in 3 320 data pairs. A second filtering step
was applied to eliminate duplicates, verify matching file names and paths, and extract the
start and end lines for each function. This process resulted in 2 985 function pairs across 468
distinct projects.
All 1 206 datapoints based on the Linux repository were removed because the project was too
big for the tools to analyze within a reasonable time.

3.2.2

Running Tools

The first step was running the SATs on Juliet Test Suite and the realistic data and capturing
their raw outputs. Automation scripts were developed for each tool to simplify this process.
Some tools, such as Clang-Tidy, require the project to be built. This is a bigger process for the
realistic data that could be read more about in Section 3.2.3.
The scripts for Juliet were iterated through each CWE-specific directory, and for PrimeVul,
they were iterated through each project. Flags and arguments were configured to ensure fairness and comparability among the tools, providing severity levels and generating machinereadable output formats. Which flags were used and arguments for each tool are presented

restricted to combinations where all other tools included in the comparison successfully executed on the corresponding data points. This ensures consistency in the evaluation and
avoids skewing the results due to missing tool outputs.

3.2.4

Filtering and Parsing

Once all raw data was collected, it was transformed into a standardized format to enable
consistent classification. A unified CSV schema was created, containing core fields common
to all tools and necessary for gathering the metrics: file name, line number, and error message.
While the analyzers often offered additional metrics, none were essential for classification and
available across all tools, so they were excluded from this standardized format. Because each
tool has different output structures and naming conventions, individual reformatting scripts
were developed to parse and map the data into the following CSV format:

xFile Location, Line, Error Messagey
Additionally, Clang-Tidy was filtered to display only security-related alerts since we are not
interested in its linting capabilities or syntax-based remarks. Similar filters were applied to
the Flawfinder output, only including entries of "warning" severity or higher. The outcome
from this section was one CSV file per tool containing the filtered and formatted results from
the full C++ test suite.

3.2.5

Classification

The next step was mapping reported warnings back to Juliet’s labeled functions. The output
generated by the SATs does not generally reference function names directly. Instead, warnings are associated with line numbers. Therefore, line-to-function mapping was performed
to determine which function each reported warning corresponded to. The evaluation was
done by iterating over the CWE files and checking, on a function-by-function basis, whether
a matching warning existed in the CSV file from each tool.
For PrimeVul, if a function is vulnerable, it is explicitly labeled within the data. Function-toline mapping was run when setting up the data. The automation then checks for each data
point to see if a result containing the vulnerable function exists. Each Juliet and PrimeVul
data function was then classified according to Table 2.1.
Some limitations were implemented to avoid modifying the results by over-counting multiple
alerts within the same function. If a single function was flagged multiple times by a tool at
different line numbers, it was still counted only once as a positive for that function. Thus, if
a vulnerable function contained multiple warnings, it contributed a single TP, while a benign
function incorrectly flagged at multiple lines counted as one FP.

Cross-Tool Combination Strategies

To evaluate how different tools combinations can be used for better performance, two strategies were considered: intersections, which highlight consensus between tools, and unions,
which aggregate all unique findings. By calculating new values for the advanced metrics
such as precision, recall, F1-score and MCC, these strategies offer insight into how multiple
tools can be leveraged to support more effective secure development workflows.
Intersections
In addition to traditional evaluation metrics, the classification intersections for various tool
combinations were computed. This approach explores whether combining multiple tools can
improve overall accuracy by “filtering out” incorrect classifications from individual tools.
The intersection eliminates classifications only found by singular tools while accepting more
commonly identified vulnerabilities detected by multiple tools. This is the same as doing a
logical AND with the output results.
18

3.3. Extended Data Processing
Intersections between tool results were calculated by iterating over the entire test suite, covering all CWEs and functions, and isolated entries where multiple tools reported the same
file, classification, and function. For PrimeVul, intersection data was computed showing how
many datapoints the different tools were successfully run on, giving some insight into how
easily the tools run on any given project.
Unions
Similarly, classification unions were computed to evaluate whether combining tool outputs
could increase overall detection coverage. In contrast to intersections, unions consider any
vulnerability reported by at least one tool, thereby accepting broader warnings. This strategy
aims to maximize coverage, even at the potential cost of introducing more FPs. This is the
same as applying a logical-OR across tool outputs.
Union analysis followed the same methodology as the intersection analysis but included all
unique findings from the participating tools rather than only shared ones. This comparison
helps to understand how tool combinations can complement one another to provide a more
comprehensive security assessment.

Discussion

This section will discuss the results presented in Section 4 and the method used to gather

5.1

Results

This chapter discusses the findings from Chapter 4. This discussion is structured around the
research questions, first focusing on the Juliet Test Suite and then examining the PrimeVul
dataset results. Subsequently, tool-specific observations will be addressed, integrating the
results from both datasets. Finally, the method used to obtain the results will be reviewed,
focusing on the challenges encountered and the measures taken to mitigate their impact on
the findings.

5.1.1

Metrics

Many different metrics are used to analyze the data; it is important to know what each metric
does and how it applies in the security context.
Fundamental metrics
The fundamental metrics of TP, FP, TN, and FN, as described in Chapter 2.1.3, are mainly
used to calculate the other metrics that give insight into the tool’s performance.
Precision
This metric gives us value in security context where FPs can lead to alert fatigue. Tools that
only raise warnings when they are very confident may achieve high precision while still
missing many probable vulnerabilities, resulting in less secure code. Precision can give a
skewed impression of tool performance if considered in isolation, especially on imbalanced
datasets where FNs are not penalized.

27

5.1. Results
Recall
Precision is a metric useful in security evaluations where missing vulnerabilities could have
severe consequences. However, precision considered in isolation can also give skewed performance since it does not penalize FPs, which could result in alert fatigue.
F1-score
Since F1-score combines precision and recall, it gives a more balanced view of tool performance when both missing vulnerabilities and generating too many false alarms are important. However, because F1-score ignores TNs entirely, it can skew results on imbalanced
datasets where TNs and FPs are few.
Pair-wise metrics
Pair-wise metrics are valuable when identifying data points that could benefit from deeper
manual analysis. For instance, pair-wise reversed predictions, where the tool flags the
patched function but misses the vulnerable one, can point to major issues in tool logic or
rule coverage.
Matthews Correlation Coefficient
MCC is a metric that is useful for both balanced and unbalanced datasets; the main advantage
over other advanced metrics is that MCC takes TN into account, which no other tool directly
does; if the dataset is balanced, precision and F1-score would indirectly take it into account
since it takes FPs into account which is the inverse [5, 15]. MCC has flaws; a saw-tooth
pattern will appear when analyzing the first-order partial derivate concerning TP for MCC
on balanced and imbalanced datasets. The shape of the saw-tooth changes based on the
value of TN. The same saw-tooth effect is seen when deriving for TN and changing the value
of TP [30]. This concludes that MCC is not a perfect metric to evaluate any dataset, but for
this study, since FN is evaluated. We have one balanced dataset (1:1) with PrimeVul pairs
and one imbalanced (1:2) with Juliet. The saw-tooth patterns are very similar, and there is
still much value in looking at the MCC.

5.1.2

Juliet Test Suite Results

The Juliet Test Suite serves as a reliable baseline for validating our methodology. Due to its
clearly labeled functions enable verification that each SAT is properly configured and that
our post-processing scripts correctly capture, filter, and classify findings as intended[2].
Additionally, using a well-known and researched test suite allows us to cross-reference our
results with earlier Juliet studies, providing a reliability check for the rest of the evaluation
before using similar methods on the more challenging PrimeVul dataset.
The classification Table 4.1 shows a large amount of TN overall. This is expected for multiple
reasons; firstly, the classifications were made per function as described in Section 3.2.5, and
most functions in the test suite are benign. Furthermore, Figure 4.1 shows that only about 5%
of functions were flagged. Given that few flagged functions are relative to a largely benign
dataset, a high number of TN is expected.
Cppcheck, Snyk, and Semgrep follow a pattern of about twice the number of TPs compared
to FPs; this pattern is then reversed for Clang-Tidy and Flawfinder, which follow the opposite
pattern of nearly double the FPs compared to their TPs, along with a higher count of flagged
functions. This indicates that they are more aggressive when detecting potential vulnerabil-

ities. In tradeoff for the worse precision, a higher recall score is found for Clang-Tidy and
Flawfinder.
Overall, the tools were largely inefficient at finding vulnerabilities in the synthetic dataset,
identifying only about 7% of the intentionally vulnerable functions.
MITRE Top 25
As shown in Figure 4.1, the tools had a comparable performance on the most common CWEs
as they did across the entire dataset. This observation is interesting, as one might expect
enhanced performance on more widely recognized vulnerabilities. However, the TP rate saw
only a slight increase of 0.5 percentage points, while the FN rate increased by 4.6 percentage
points, suggesting that the tools performed slightly worse on the vulnerabilities in MITRE
Top 25.
Advanced Metrics
Table 4.3 presents the precision, recall, F1-scores, and MCC for each tool. These metrics
provide a more balanced view of performance than raw classification counts, as they highlight the trade-offs between detecting genuine vulnerabilities (recall) and correctly identifying them (precision) [27].
Most tools report moderate to high precision, ranging from about 33% to 68%, but with low
recall between 1.5% and 14.9%. This suggests that, while many of the flagged issues are
correct, a large portion of actual vulnerabilities are still undetected. Practically, this means a
high risk of potential security issues going unnoticed.
The F1-score is below 21% for all tools, indicating a low general performance for vulnerability
detection on the Juliet Test Suite. The MCC gives us some insight by considering TPs, FPs,
FNs, and, unique to this metric, TNs. Having a metric that takes all four of the basic metrics
into account is extra important when analyzing an imbalanced dataset such as the Juliet Test
Suite. The tools have a spread from 0.14 down to 0.02, giving quite a high variance in values;
however, they are far away from a perfect prediction, which would be a value of 1. However,
since all tools are above 0, they all have predictive capability. Due to the low numbers, the
predictive capability is very close to random guessing.
Classification Intersections
Looking at Table 4.4, we see that although single-tool usage detects many vulnerabilities,
it also produces a large number of FPs. The more tools producing the same classification

5.1.3

PrimeVul Dataset

In comparison to the Juliet Test Suite, we only used the pair-wise dataset from PrimeVul,
leading us to have 50% benign and 50% vulnerable functions, with each function being before
and after the patch correcting the vulnerability. The functions are based on realistic historical
data, meaning the complexity of each function is similar to what would be expected in a realworld project. This is reflected in only 1.6% of functions being flagged. Due to the low amount
of flagged functions, we deemed that further quantitative analysis of the results would not
be meaningful. This means the MITRE Top 25 analysis was not performed, and no analysis
based on the intersection counts results was performed.
Historic data
One reason for the poor results on PrimeVul could be due to a lot of open-source projects
running some SAT before the change is accepted into the central repository, as described in
Section 2.2.2. This could mean that the easier vulnerabilities are found and fixed before they
are merged, resulting in only complex vulnerabilities making it past the automated tools, thus
making the dataset only contain complex vulnerabilities. However, to enable a meaningful
comparison and gain insight into real-world performance, this trade-off was accepted. Moreover, openly available, untested real-world code is scarce, largely because of understandable
security concerns.

5.1.4

Tool-Specific Observations

This section discusses the specific characteristics and behaviors of each tool, aiming to connect
their underlying techniques with the observed results. By analyzing their internal approaches
and reported metrics, we can better understand the potential reasons behind their respective
performances.
Clang-Tidy
Clang-Tidy’s AST-based approach enables it to flag a larger range of potentially vulnerable
patterns, contributing to its highest number of TPs (15 996) among the tested tools. Using
many checks results in broader coverage but introduces a large number of FPs (32 506), resulting in a relatively low precision (32.9%) and high recall (14.9%). Issues and questions
related to FPs from Clang-Tidy are common, and they have a webpage providing fixes for

30

5.1. Results
the most common ones1 . However, these fixes are mainly on a per-case basis and thus were
not included in the study due to the large-scale nature of the dataset.
Clang-Tidy is especially interesting since it has been outperforming the other tools in precision, recall, and F1-score but is dead last in MCC with only 0.02. Since MCC is the only value
accounting for a higher FP rate, this statistic is important in an unbalanced dataset.
Cppcheck
Cppcheck is focused on finding undefined behavior and potential security vulnerabilities in
the code through a comprehensive list of checks2 . Cppcheck uses checks and unsound flowsensitive analysis as described in Section 2.1.2, which resulted in 6 687 TPs.
Cppcheck does not perform exhaustive exploration, potentially causing missed vulnerabilities, but helps maintain a lower FP count of 3 073. Overall, this approach explains why
Cppcheck flags fewer overall vulnerabilities compared to more aggressive or simpler patternmatching tools, which trade detection for fewer false alarms. Cppcheck was run once without
a compiled database and once with each data point due to the similar result when running
the tool with a compiled database, as without it, it was excluded from the results section.
Flawfinder
Flawfinder uses a straightforward pattern-matching approach that allows rapid analysis but
significantly contributes to its high FP count (11 104). The benign code is incorrectly flagged
due to the lack of contextual understanding. Despite this limitation, Flawfinders simplicity
means it requires minimal setup and and still runs efficiently with little configuration which
could make it useful in situations where there is little time to set-up a more complex SAT.
Semgrep
Semgrep marked a relatively small amount of functions (2 547) compared to other tested tools
but mainly had correct marks as identified by its precision score of 67.1%. One potential reason that Semgrep flagged so few could be that the default rule set for C / C++ that Semgrep
uses only has 53 rules3 . The Semgrep team curates these rules and is quite targeted, leading
to a better precision than most other tools with larger rule sets. Downloading and adding
more rules could lead to more vulnerabilities being found while also increasing the amount
of FPs.
Snyk
The combination of data-flow and control-flow analysis with predefined security rules could
lead to the accurate detection of vulnerabilities, significantly reducing FPs, totaling 3 631.
Relying on learned patterns and rule definitions also leads to missed vulnerabilities, with a
TP count of 6 074. The Snyk analysis need to be analyzed especially close due to the limited
amount of runs that were had meaning the entire dataset could not be analyzed.

5.1.7

Large Language Models & AI

In addition to SATs, this study also evaluated the performance of two prominent LLMs on
vulnerability detection. The methodology and results are described in more detail in Appendix A. However, these findings were excluded from the central part of the report.
We chose not to directly compare the language models with the SATs, as their approaches
differ significantly. For instance, SATs are given full context, analyzing entire projects or files
where vulnerabilities occur. They also output information in addition to classifying vulnerabilities, such as type, affected lines, and severity. In contrast, the language models were given
only isolated function strings to classify as vulnerable or not. This limited input reflects the

structure of the PrimeVul dataset, which is designed for machine learning. Furthermore, giving LLMs a broader context quickly leads to practical constraints related to model size and
computational resources.
Additionally, the PrimeVul dataset is split into training, validation, and test sets, and these
splits are used to fine-tune the models. As a result, less data is available for final evaluation
compared to the static tools, which can be tested on the entire set of benign and vulnerable
function pairs.
These substantial differences in context, data availability, evaluation scope, and methodology
make a direct comparison between LLMs and SATs unfair.

5.2.1

Replicability

Ensuring reproducibility was a central focus of this study, leading to the development of
numerous scripts. These scripts range from large-scale automation tools for data collection
to smaller scripts that handle tasks that could be done manually, such as merging training,
test, and validation data into a single file. Since our results for the Juliet Test Suite align with

in turn strengthens the reliability of our results on the PrimeVul dataset.

5.2.2

Source criticism

Throughout this work, we have primarily relied on peer-reviewed sources to ensure the credibility and academic integrity of the research. Initially an exception was made for the source
for the PrimeVul dataset which was a preprint since it was the largest dataset based on realistic data. However it was peer-reviewed and presented in a conference in May 2025, prior to
this study.

5.2.3

Threats to validity

Several factors may impact the validity of this study’s findings. The following subsection
outlines specific threats to validity identified during the research process and discusses the
steps taken to mitigate their impact.
lack of manual verification
The first threat is the lack of manual verification of the output of the SATs. If a tool reports
any vulnerability within the marked function, it will count. The automation process does
not check what kind of vulnerability was reported; it only checks if it was reported at all.
Therefore, a tool might report the wrong vulnerability in the correct function, and it will still
count as a TP. Some manual verification was performed, as explained in Section 5.2.3, but a
higher level of manual verification for both Juliet and PrimeVul would take too much time
for the span of this thesis. Based on a preliminary review of the results, this appears to have
had a minimal impact on the overall findings.
Different tool outputs
The second issue arises in how different tools produce warnings. For example, if there is a
memory leak issue, some tools would report it where the memory was created and some at
the end of the function when the memory was not freed. This was solved by annotating that
the vulnerable area is the entire function. This was done in part for this reason and partly

33

5.2. Method
because the ground truth given for PrimeVul was on the function level, so it was reasonable
to have the same level across both of our datasets. This could lead to the first threat to validity
to increase.
Additional Vulnerabilities
Another threat to the validity of both datasets is that there is at least one confirmed vulnerability; it is tough to guarantee that the source code does not contain additional, undetected
security flaws. This risk grows larger for the PrimeVul dataset that is based on realistic historical code where a piece of code can be deemed benign for a long time and later found
vulnerable, such as the heartbleed vulnerability4 . There could also be vulnerabilities that are
undetected in the benign labeled data point. We minimize this risk by keeping the level we
are analyzing as small as possible on a function level instead of a file level and minimizing
the area where rogue vulnerabilities could be found, as well as using freshly labeled ground
truth with PrimeVul, which was created in 2024.

Verification
To ensure accurate classification for both synthetic and real-world data, spot-checks were

5.3

The work in a wider context

As software security grows increasingly critical in our rapidly digitalizing world, understanding the limitations and capabilities of security tools plays a crucial role. Gathering information about how SATs perform on realistic data could inform developers using SATs of
the limitations, and the following areas are mitigated.

5.3.1

Security fatigue

Security fatigue occurs when maintaining security becomes too complex or burdensome for
users, even when protocols are in place [14]. In the case of SATs, this could mean that running
multiple tools and addressing every reported issue becomes overwhelming for developers.
This highlights the importance of understanding the accuracy and reliability of these tools.
A situation may arise where a developer must sift through nine FPs to identify and fix one
TP, leading them to question whether the effort is worthwhile due to the fatigue it causes.
However, in industries where high-security standards are critical, every flagged issue must
be carefully reviewed to ensure that no TP is overlooked.

5.3.2

Automation in security

One of the motivations behind this study is that approximately 50% of open-source projects
use SATs [1]. However, as the results demonstrate, many vulnerabilities remain undetected.
The risk lies in developers assuming that no vulnerabilities exist simply because SATs do not
flag any issues, creating a false sense of security. Over-reliance on automated tools without
manual verification can be dangerous, as it may leave critical security flaws unidentified.

5.3.3

lack of tool transparency

A major challenge in evaluating SATs is the lack of transparency regarding how these tools
detect vulnerabilities. This is particularly true for AI-driven SATs, as AI models are inherently black-box systems, making it difficult to understand their decision-making process.
Additionally, subscription-based SATs often provide only broad, high-level descriptions of
their internal workings without offering detailed insights into their detection mechanisms.
In contrast, open-source tools are not designed for profit and do not actively advertise their
technologies. While some information about these tools can be found in their documentation,
it is often written primarily as a byproduct of explaining how to use the tool rather than as
a description of how the tool actually works. This lack of clarity can make it challenging for
developers to fully trust or optimize the tools for their specific security needs.

Conclusion

The primary purpose of this thesis has been to evaluate SATs based on different technologies
when applied to synthetic or realistic data. The study shows that SATs detect only a small
fraction of C/C++ vulnerabilities, especially in real-world code. The tools evaluated were
Clang-Tidy, Semgrep, Snyk, Cppcheck, and Flawfinder on the synthetic dataset Juliet and the
realistic dataset PrimeVul. This chapter answers the research questions and outlines future
work.

6.1

Research questions

The following section will present answers to the questions posed in Section 1.3, based on the
results in Chapter 4 and the discussion in Chapter 5.

6.1.1

RQ1.1: How do static analysis tools based on different technologies
perform when applied to synthetic datasets?

When applying SATs to synthetic datasets, most tools demonstrated limited predictive capabilities. The highest F1-score observed was 20.5%, achieved by Clang-Tidy, while the highest
Matthews Correlation Coefficient (MCC) was 0.14, recorded by Cppcheck. These figures suggest that while certain tools can identify specific vulnerable patterns present in the synthetic
dataset, their overall effectiveness is still limited.
Combining multiple tools can improve precision at the cost of a total number of correctly
identified vulnerabilities decreasing. For instance, the intersection of Snyk, Semgrep, and
Cppcheck achieved better ratio between TP and FP, indicating that agreement across tools
may point to more reliable findings. This improvement is by no means consistent across
different tools, as combining Snyk, Clang-Tidy and Flawfinder results in more FP than TP.

6.2. Future work

6.1.2

RQ1.2: How do static analysis tools based on different technologies
perform when applied to real-world projects?

The performance of SATs on real-world data was significantly worse than on synthetic
datasets. The highest F1-score, 8.4%, was again achieved by Clang-Tidy, while the top MCC
was just 0.007, reported by Semgrep. This indicated a performance comparable to random
guessing. The tool that flagged the most functions was Flawfinder, with 103 marked data
points out of 4 764 in the dataset. However, the overall detection rates are so low that any
fine-grained analysis becomes difficult to justify. These results highlight a limitation in current SATs when applied to complex real-world source code and underline the need for improvement in both tool capability and evaluation methods.

6.1.3

Updated Dataset

The realistic component of this study is based on the pairwise-labeled portion of the PrimeVul dataset. During the preparation phase, several issues were identified within the original
dataset, prompting preprocessing and cleanup steps as outlined in Section 3.2.1. These included removing unreachable projects and ensuring accurate line-level mapping.
To support future research and reproducibility, a cleaned and preprocessed version of the
dataset is made publicly available1 .

6.2

Future work

While this thesis provides a comprehensive evaluation of SATs on both synthetic and realworld datasets, it also raises important questions and identifies several areas for further research. These will be ordered below from most important to least important.

6.2.1

What is the best method to evaluate and compare SATs?

Every dataset used for evaluating SATs presents some form of limitation. Synthetic datasets,
such as Juliet, are often less complex in terms of data flow and contain bugs that are overly
distinct or simplified compared to those found in real-world code.
The realistic dataset used in PrimeVul suffers from the fact that it originates from open-source
projects, where automated SATs may already have been applied before the code is merged.
This means that the code in the main branches may have already been filtered by such tools,
potentially reducing the number of detectable vulnerabilities. If a vulnerability is old and
easily identifiable through known rule sets, modern tools might already have incorporated
specific detections and skewing evaluation.
Another possibility is using a method where vulnerabilities are injected into realistic code [9].
This suffers from much of the same problems as synthetic data, such as simplistic and distinct
bugs, but it fixes the issues of simplistic and unrealistic dataflow.
Currently, a good dataset combines realistic, synthetic, and injected vulnerabilities in a way
that enables a holistic and unbiased evaluation of SATs. Such a dataset would overcome the
weaknesses of both synthetic and historical sources. However, identifying or creating such a
dataset remains a non-trivial challenge and an important direction for future work.

6.2. Future work

6.2.2

Creating a new tool

Given the bad results of these tools another possibility for future work is the development
of a new SATs tailored specifically for vulnerability detection in modern software systems.
A new solution could focus on addressing the limitations identified in both rule-based and
learning-based tools, potentially combining their strengths in a hybrid approach. Emphasis
could also be placed on improving usability, configurability, and transparency, particularly in
tools designed for open-source or resource-constrained projects.

6.2.3

More languages and more Tools

A natural direction for future work involves expanding the scope of static analysis evaluations to include a broader range of programming languages and analysis tools. This study
focused exclusively on C and C++ code, primarily due to the structure of the datasets and the
availability of well-established tools targeting these languages. Software systems are written
in more languages than C/C++, such as Python, Java, Rust, or Go, each with unique security
characteristics and common vulnerability types. Evaluating SATs across multiple languages
would provide a more comprehensive understanding of their generalizability and practical
applicability in diverse development environments.
Moreover, this study only examined a subset of available tools. Looking into other commercial solutions and newer machine learning-based models may offer improved detection capabilities and adaptability. Furthermore, investigating how the tools are integrated into modern
CI/CD pipelines would be interesting since a lot of projects use some sort of automated SATs.
Such a study could likely use a similar approach to the one in this paper.
Another area to explore would be expanding the study beyond static analysis to include
methods such as dynamic analysis. Dynamic analysis can provide real-time feedback and detect issues that static analysis might miss. However, this approach would require the projects
to be built and executed as part of the analysis process.
Finally, further research could explore hybrid approaches that combine static and dynamic
analysis or integrate multiple tools into a unified pipeline. Understanding how these multitool or multi-technique strategies perform compared to standalone tools could significantly
benefit both researchers and practitioners aiming to optimize their security workflows.

A Large-Language Models

AI and large language models (LLMs) are becoming increasingly popular in software development due to their effectiveness and ability to perform a wide range of tasks. In this study,
we evaluate two transformer-based LLMs, CodeBERT and T5. These models are fine-tuned
for binary classification to detect vulnerabilities in source code. They were selected for their
popularity, demonstrated effectiveness in recent research, and relatively low computational
cost for fine-tuning compared to larger models [8, 28].
CodeBERT
CodeBERT is a bimodal transformer trained on paired natural language and code across six
programming languages [13]. Its pretraining objectives enable it to capture both syntax and
semantic relationships in code, making it a strong candidate for vulnerability detection.
T5 / CodeT5
T5 is a sequence-to-sequence transformer that treats every task as text generation [26].
CodeT5 adapts this model for source code, pre-trained on large GitHub repositories [29]. This
allows it to better model code semantics and perform well on various software engineering
tasks, such as vulnerability detection by code classification.
Dataset
Pretrained models were retrieved from the HuggingFace model repository 1 ,2 . The PrimeVul
dataset, conveniently partitioned into training, validation, and testing subsets, was used to
fine-tune and evaluate the models 3 .

Discussion
Compared with the study by Ding et al.[8], we obtain much lower accuracy but pairwise
scores as seen in Table A.4. A likely reason is that the PrimeVul authors evaluated on the full
test set which is heavily imbalanced, with about 97% benign and only 3% vulnerable functions [8]. Its relatively simple to get high accuracy on such an imbalanced test-set, because
classifying every function as benign would lead to 97% accuracy while not finding a single
vulnerability.
Our study used the balanced PrimeVul test set with a 50/50 split for a fairer comparison
against the SATs. Furthermore, the balanced test-set only contains functions that have over
80% string similarity between the vulnerable and benign versions, making the differences so
small and subtle that they might be harder for LLMs to detect. Our models also flag slightly
more vulnerabilities than the PrimeVul ones, possibly because of the different class weights.
Conclusion
During evaluation, The Matthews correlation coefficient remained close to zero, indicating
performance close to random guessing. In practice, this means the models identify only one
vulnerability in five and miss most flaws. The warnings they generate also lack the contextual
details such as CWE labels, suspect lines, and remediation hints that SATs provide. Overall,
these fine-tuned LLMs perform only on par with, and often worse than, conventional static
analyzers while providing less information.
