SUMMARY
A multi-output instruction (MOI) is an instruction that produces multiple outputs to its destination locations.
Such inherently parallel instructions are becoming more and more popular in embedded processors, due
to the advances in application-specific architectures. In order to provide high-level programmability and
thus guarantee widespread acceptance, sophisticated compiler support for these programmable cores is
necessary. However, traditional tree-based approaches for instruction selection, although very fast, fail to
exploit MOIs mainly because of the fundamental limitation of the tree representation. In fact, to generate
optimal code with MOIs requires a more general graph-based formulation of the instruction selection
problem, which is at least NP-complete. In this paper we present a new methodology to automatically
generate from simple instruction set descriptions, graph-based code selectors that can effectively utilize
all provided instructions including MOIs. Our experimental results using a set of benchmarks on a target
processor with various MOIs of up to two outputs demonstrate that our generated code selectors can
quickly and effectively exploit many MOIs at the application level, and therefore are highly desirable
both for architecture exploration and as code generators after architecture is fixed. Copyright q 2010

1. INTRODUCTION
Since the last decade Application-Specific Instruction-set Processors (ASIPs) are being widely
used as programmable accelerators used in Systems-on-Chips (SoCs) for various applications in
multimedia, signal processing, network, and cryptography domains. In order to meet the stringent requirements of such applications, ASIPs often provide a set of new instructions, tailored
to the needs of their target applications. The predominant feature of these custom instructions
is inherent parallelism. The custom instructions comprise several operations that are executed in
parallel and can produce multiple results at the same time. Consequently, they are referred to as
Multi-Output Instructions (MOIs). Whereas simple instructions (Figure 1(a)) and chained instructions (Figure 1(b)) can be represented as trees, MOIs will always have a fanout larger than one
(Figure 1(c)) and can only be represented as a DAG (Directed Acyclic Graph).

In the area of digital signal processing, MOIs are already a natural way to increase performance.
Prominent examples are instructions to support simultaneous access of different memory banks.
For example in Sony pDSP processor, an instruction such as PLcDXY r1,@a,r2,@b, can load
variables a and b simultaneously into registers r1 and r2. These MOIs can access memory
faster by performing loads/stores in parallel on partitioned memory banks via multiple data and
address buses. ASIP designers prefer such techniques over more complicated hardware mechanisms.
By encapsulating parallel operations in an MOI, impressive speedups can be achieved without
sacrificing too much flexibility toward different applications [2]. On the other hand, the increasing
complexity of embedded applications makes it prohibitively difficult to implement them in assembly
language. Sophisticated compiler support for such processors is, therefore, strongly required in
order to guarantee fast application development and ensure customer acceptance for the processor.
The main issue with compilers supporting inherently parallel instructions is how to do code
selection for those instructions. Code selection typically assumes that all instructions have tree
patterns, and applies tree parsing [3] on application’s Data-flow Trees (DFTs). Since MOI instructions cannot be modeled with tree patterns, they cannot be supported or optimally selected by
tree parsing, which can significantly limit the design space of ASIPs. Moreover, the scope of tree
parsing is restricted to one DFT. Consequently, instructions having functionality that exceeds the
scope of one DFT cannot be matched by tree parsing. In order to overcome these limitations,
the scope must be extended to at least the size of a basic block, which is then represented as a
Data-flow Graph (DFG). Unfortunately, pattern matching on a DFG is NP-complete in general [4].
Typical approaches to solve this problem rely on Compiler Known Functions (CKFs) and Inline
Assembly. In both cases the application must be modified manually, which may be impractical for
large applications.
In addition, the extremely heterogeneous landscape of application-specific architectures demands
highly flexible programming tools. Such architectures are usually developed in an iterative manner
during which the architecture is incrementally refined. This iterative development flow requires
compilers to be easily retargetable in order to support an arbitrary set of instructions during
processor development. There exist several code-generator generators, such as Burg [5], Iburg [6],
and Olive [7], which accept tree grammar modeling the instruction set of the target processor
architecture and produce code-selector programs in C. Such code-selector programs can be very
comfortably integrated into existing compiler backends. However, since those generators allow
tree grammars only modeling instructions with tree patterns, the produced code-selectors lack the
capability of exploiting MOIs, which means manual code modification to explore MOIs.
In this paper, we present a new tool that extends the concept of tree-based code-generator
generator toward a graph-based one, called Cburg. We extend the grammar of the instruction set
description to include more general DAG patterns so that MOIs can be modeled and matched.
Thus with Cburg it is no longer necessary to manually modify code using inline assembly or
CKFs for architecture exploration, which can greatly facilitate ASIP design cycle as illustrated
in Figure 2(b). We have integrated Cburg into the LCC compiler [8], a widely used retargetable
compiler. Our experiments using the integrated LCC compiler extended to include various MOIs
with two outputs on a set of benchmarks from cryptography and digital signal processing domains
demonstrate that our proposed code selection algorithm can profitably utilize MOIs as well as

2. RELATED WORK
Owing to the limitations of tree parsing, several attempts have been made to provide a generalization of tree-based code generation. In [9], an optimal graph-based code selection is proposed
for regular data path architectures without instruction level parallelism. However, ASIPs often
feature irregular Instruction Set Architectures (ISAs) comprising parallel instructions. Specifically,
targeting digital signal processors, where it is most natural to have MOIs, Araujo et al. [10] propose
an algorithm to optimally break up DFGs into expression trees taking into account their target irregular architecture. However, their method is not universally applicable to any application-specific
architectures or even any DSPs. Davidson et al. [11] introduce a code selection algorithm based
on peephole optimization, which can potentially deal with MOIs. However, their method does not
consider how to select the best set of MOIs in the presence of overlapping MOI candidates. Leupers
et al. [12] show that tree parsing leads to suboptimal results in the presence of MOIs, and propose
a new technique based on the splitting of instructions into register transfer primitives and recombining these primitives in an optimal manner using integer linear programming. Liao et al. [13]
also solve the same problem by augmenting a binate covering formulation. Unfortunately, both
approaches [12, 13] have exponential time complexity in the input DFG size and are not scalable.
Liem et al. [14] propose a graph-based instruction selection methodology that features a flexible
pattern representation style. This style includes data-flow, control-flow, and mixed data/controlflow information. Eckstein et al. [15] describe a code generation method based on SSA form for
complete functions in order to take control flow information into account. Their work differs from
ours in that they target Very Long Instruction Word (VLIW) processors, whereas we target more
general embedded processors with various types of MOIs, where simple VLIW-style operation
merging to create longer instruction words may not work due to scheduling dependency. Such
constraints are considered in our work in our interference analysis, which includes scheduling
dependency check (see Section 4.3.1). A recent approach [16] to graph-based code generation
uses unate covering to generate compilation for hardware accelerators. However, as they consider
connected instruction patterns only, MOIs, which may be disconnected, are not in their scope.
It may be tempting to use a simple peephole optimization or micro-code compaction algorithms
such as [17] to generate MOIs by combining SOIs after tree-parsing. However, finding optimal
instruction covering is much more complicated than that because a SOI may contain multiple
operations, called chained instruction (see Figure 1(b)), and due to encoding constraint only some
combinations of SOIs may be defined as MOIs. To further complicate the matter, MOIs sometimes
use register subclasses as their operands to save the encoding space. Thus optimal SOI covering

depends on what MOI covering will be, and in general it is not possible to find the optimal covering
while separating the two. Recently Ebner et al. [18] consider instruction selection problem in the
presence of MOIs, and their approach is to formulate the whole problem as a Partitioned Boolean

their solution requires intermediate representation of SSA (Static Single Assignment) form, which
may not be available in all compilers. Our approach is to use the existing tree-parsing framework,
which is efficient, widely used, and optimal for SOI instructions, but complement it by adding a
quick handler for MOI instructions.
To summarize, the existing approaches either take exponential compilation time, or do not
consider inherent instruction parallelism producing multiple results, which must be considered
to emit MOIs during code generation. Our contribution in this work is the presentation of a
new instruction selection algorithm that exploits inherent parallelism provided by the underlying
hardware so as to generate MOIs. More importantly, we present a new code-generator generator,
Cburg, which is an indispensable component of a compiler that must be retargeted rapidly to
explore a diversity of ASIP architectures. The basic structure of Cburg is virtually identical to
existing code-generator generators like Iburg or Olive, but the differences are first the expressiveness
of accepted input grammars and second, the produced code selector to match IR-patterns. The
expressiveness of the Cburg’s grammar is stronger than those of the ordinary tree grammars.
Furthermore, Cburg produces C-code for a graph-based code selector from the received grammar
such that the matching scope for pattern matching is not limited to single statement trees. Besides,
the generated code selector’s average runtime is linear in the size of the input DFG. While our
earlier work [1] also proposes a rule grammar that supports some MOIs, it is restricted to MOIs
consisting of parallel, disconnected SOIs, but in this work we extend it to include more general
MOIs such as SOIs connected with shared operands. Overall, we have observed that our approach
results in an easily retargetable graph-based code generator, thus enabling compiler designers to
quickly provide new compiler backends for ASIPs with irregular ISAs.

3. CBURG RULE DESCRIPTION
We now present the rule description for Cburg, our graph-based code-generator generator, which
is followed in the next section by our code selection algorithm for MOIs.
3.1. SOI rule
In Olive, instruction selection on a DFT consists of two main phases: matcher and cover. The
matcher phase traverses the DFT in a bottom-up manner and applies a tree grammar in order to
annotate rules at each visited node, according costs and resulting nonterminals that can be used
to match it. The cover phase then traverses the DFT in a top-down manner and takes advantage
of the annotated information for the selection of the rule with minimal costs for each node. For
every hardware instruction that can be described by a tree IR, a rule exists in the tree grammar of
the form [6, 7]:

easily tree-covered by an existing tree parser. First, in the MOI candidate identification step, all IR

the list of MOI candidates and the member IR nodes of each MOI candidate. Second, the MOI

4.2. MOI candidate identification
The first step of our MOI code selection process is to annotate each IR node with a list of matching
split rules and SOI rules. Figure 4 illustrates this with an example. In (b) node N1 is annotated
with split rule RC1 as well as SOI rule R A . After this annotation, a table called split rule map is
created which maps each split rule to the set of corresponding IR node instances (see Figure 4(c)).
From the split rule map, it is easy to form MOI candidates. Simply, combine split rules belong to
an MOI rule, by pairing the corresponding IR nodes of the split rules, as illustrated in Figure 4(d).
Each pairing of the IR nodes defines an MOI candidate, and the IR nodes that together define an
MOI candidate are called member nodes of the MOI candidate. While initially a large number
of MOI candidates are generated, those that do not pass validity check are eliminated. Validity
check determines if there is data dependency between the member nodes that is not preserved in
the MOI implementation. In our example MC2 and MC5 are eliminated because they fail in the
validity check.
4.3. MOI candidate selection
To select the most profitable MOI candidates we consider in this step two factors: benefit and
interference. Benefit is determined for each MOI candidate individually, whereas interference must
be considered between multiple MOI candidates. Once benefit and interference relations for all the
MOI candidates are analyzed, the problem of selecting the most profitable set of MOI candidates
can be formulated as a Maximum Weighted Independent Set (MWIS) problem, which is NPcomplete. Thus we apply a heuristic called GWMIN2 to solve the problem. Finally the result of
this step is a set of MOI candidates that have no interference with one another, meaning that they
can all be converted into corresponding MOIs at once without violating schedulability or any other

4.3.1. Interference analysis. We must select MOI candidates carefully for a valid covering in a way
that none of the selected ones interfere with each other in the cover. We classify the interference
into two types: covering interference and scheduling interference. We represent the interference
relationship with a graph, called interference graph IG = (V, E), where V is the set of all MOI
candidates, and each undirected edge (vi , v j ) in Ebetween two vertices vi and v j in V represents
covering or scheduling interference.
Covering interference: If two or more MOI candidates share an IR node as their common
member node, the MOI candidates should not be selected simultaneously. For instance, in Figure 4,
MC1 and MC4 have an IR node N3 as their common member node. In this case we cannot select
MC1 and MC4 simultaneously because if we do, N3 would be covered twice, which is wrong as
it deviates from the original program semantics. In fact, only one of the MOI candidates may be
selected. This is called covering interference. Handling covering interference is easy: we add an
edge in the interference graph for every pair of nodes (MOI candidates) that share one or more IR
nodes.
Scheduling interference: Scheduling interference exists between two or more MOI candidates
if their schedule ordering graph contains a cycle. Schedule ordering graph is a directed graph,
where nodes represent MOI candidates and edges represent schedule precedence constraint (partial
ordering) due to the data dependence between the MOI candidates’ member nodes. For example,
let us assume that from the IR trees in Figure 5(a), three MOI candidates are derived as listed in
Figure 5(b). Then the schedule ordering graph has three nodes (for the three MOI candidates) and
three edges as shown in Figure 5(c), with edge (Nb , Na ) responsible for edge (MC z , MC x ), and
so on. The existence of cycle in schedule ordering graph means that there is no feasible schedule
if all the MOI candidates in the cycle are selected; at least one MOI candidate in the cycle has to
be unselected. This is called scheduling interference. To handle scheduling interference we choose
an edge in the cycle, and add a corresponding edge in the inference graph, so that at least one of
the two MOI candidates connected by the edge will not be selected.

of compatible MOI candidates with maximum profit (or equivalently, maximum benefit sum). We
say two MOI candidates are compatible if they do not interfere with each other. In our example,
we have six sets of compatible MOI candidates: {MC1 , MC6 , MC8 }, {MC1 , MC9 }, {MC3 , MC8 },
{MC4 , MC8 }, {MC4 , MC9 }, and {MC6 , MC7 }. Notice that a set with a single MOI candidate—say

profit—say {MC1 , MC6 , MC8 }—always subsumes the set. In our example, set {MC1 , MC6 , MC8 }
has the largest profit of 3. The problem of selecting such an MOI candidate set can be easily

collection of vertices that are mutually non-adjacent.

4.4. Labeling
IR nodes belonging to an MOI candidate are non-tree shaped, and thus they as a whole cannot be
recognized by the tree parser. The only way for an MOI candidate (or an MOI rule) to participate
in the parsing is via its tree-shaped split rules. That is, during tree parsing, in lieu of an MOI
rule, its split rules compete individually with other SOI rules at each tree node to be selected
as an instruction by the parser. Moreover since SOI rules can also contain multiple operations,
MOI rules cannot be said to be always beneficial than SOI rules. For these reasons, after the most
profitable set of MOI candidates is obtained, we assign some cost to every split rule sri of the

4.5. Pre-covering
Owing to the inherent complexity of MOI rules, there can be some IR nodes that belong to
selected MOI candidates (in the selection step) but are not finally labeled as MOI candidates (in

achieve this, the cover phase of a tree pattern matcher is simulated and if a member node in an
MOI candidate is not covered by any split rules, all IR nodes of the MOI candidate are re-labeled
by equivalent SOI rules. Owing to different nonterminal requirements of subsequent IR nodes,
a member node might not be covered by a split rule although the split rule has minimal costs

as illustrated in Figure 10(c). As R X 2 can be used for covering, only together with R X 1 , we should
now drop both R X 1 and R X 2 . Thus both the split rules are eliminated and all member nodes are

5. RETARGETABLE COMPILER WITH CBURG
Cburg is built on top of Olive [7], a tree-based code-generator generator, which takes a configuration
file as input and produces a set of data structures and code-generation functions for the given target
ISA. Whereas Olive’s code selector works only on DFTs, Cburg’s is designed to work on DFGs
so as to recognize MOIs. The configuration file contains the description of the target ISA in terms
of operation patterns as well as a set of functions, necessary to access the compiler’s IR. The
operation patterns form the grammar that is used to identify similar patterns from the compiler’s
IR and map them to adequate assembly instructions or lowered IR. The generated data structures
and functions provide compiler designers with a complete code generator based on our algorithm
for the target ISA, and allow for easy implementation of instruction selection for a wide range of
target machines with various custom instructions. Thus it greatly facilitates ISA exploration for
ASIP design, especially for those with MOIs.
Figure 13 gives the overall structure of our compilation framework. The framework is divided
into two phases: code-generator generation and instruction selection. First, in the code-generator
generation phase, a set of SOI and MOI rules is given to Cburg as input, and the instruction
selector is produced as output. In this phase, split rules are extracted from each MOI rule, and rule
numbers, which act as their identifiers, are assigned to them. In the instruction selection phase,
the newly generated instruction selector uses all the rules including split rules to find candidate
IR nodes, representing the operations that are performed as part of MOIs. The instruction selector
produced by Cburg consists of the matcher and the cover in much the same way as Olive. The
cover is virtually the same as that of Olive, but the matcher has been modified to handle MOIs.
In many architecture design platforms developed so far [20–23], design flow iterations usually
comprise compilation, simulation and profiling of applications for a certain virtual architecture
prototype. Based on the profiling results, bottlenecks are identified, the instruction pipeline is finetuned and customized instructions are added to stepwise improve the architecture’s efficiency, as
illustrated in Figure 14. New, custom instructions can be added to the compiler in order to evaluate
their benefit for the targeted applications during the next compilation-simulation cycle. While in
the traditional systems employing tree-based code-generator generators, only SOIs can be easily
recognized by the compiler, leaving MOIs in the realm of architects’ manual exploration, in our
proposed flow using the graph-based code-generator generator, MOIs can be as easily supported
by the compiler, allowing for much more efficient and effective exploration of the vast design
space of ASIP processors (see Figure 14).

A potential problem with our approach having two rounds—first among MOI candidates and then
between selected MOI candidates and SOIs—is that it might not achieve the global optimum
due to the phase coupling and may need some iterative approach to achieve a better result. We
have already seen an example in Section 4, where some of the selected MOI candidates were

deselected MOI candidates during pre-covering, and unless deselected ones are known beforehand,
there seems to be no way to determine during MOI candidate selection what choice of MOI
candidates would result in the most profitable final code.
Thus it is worthwhile to try an iterative approach and see how much better it can be over the
non-iterative version. Our iterative version works as follows. In the pre-covering step, if there
are one or more MOI candidates that are deselected because their member nodes are not entirely
covered, we go back to the MOI candidate selection step and do the selection again excluding
the deselected ones. This iteration is repeated until there is no deselected MOI candidate during
pre-covering.
Certainly the iterative approach gives better results. In our earlier example there were four
MOI candidates MC3 , MC4 , MC7 , and MC9 which were not selected in the selection step (see
Figure 11(b)). To give second chances to these MOI candidates, our algorithm draws a new
interference graph without deselected MOI candidates in the previous iteration, as shown in
Figure 16(a). Then applying the MOI candidate selection algorithm again, we get a new MOI
candidate set {MC1 , MC9 }, none of which is deselected later, as shown in Figure 16(c). The final
emitted code is the same as the improved code in Figure 15.
The compile time will suffer in the iterative approach. In the worst case, the MOI candidate
identification step takes O(nm ) time where n is the number of IR nodes and m is the maximum
number of split rules in an MOI. The MOI candidate selection step has a linear time complexity,
since a greedy heuristic is used to solve the MWIS problem. Therefore, the overall time complexity
is O(nm ) in the non-iterative approach. In the iterative approach, the number of iterations can be
nm in the worst case if all MOI candidates are deselected one by one in each iteration. Thus the
overall code selection takes O(n2m ) in the worst case. Assuming that an MOI consists of two
or three split rules, m can be approximated to two or three, which gives O(n4 ) or O(n6 ) time
complexity for the iterative version.

7. EXPERIMENTS
We have implemented Cburg, our proposed MOI code selection methodology, and integrated it
into the LCC compiler [8]. To evaluate Cburg, we use these benchmarks from different domains
including cryptography, network, digital signal processing, and communication: Data Encryption
Standard (3DES), Advanced Encryption Standard (AES) [24], Secure Hash Algorithm (SHA), an
internet protocol (IP) stack (which includes an IPv6-layer with authentication and encryption, as
well as an Ethernet layer), and several benchmark kernels (ADPCM, complex update, fir2dim,
matrix1x3, and n complex update) from the DSPStone benchmark suite [25].
For the base ISA, we use the MIPS architecture [26], and extend it by adding new MOIs. To
come up with the best set of MOIs, we profile all benchmarks with a fine-grained profiler [27]
to identify execution hot spots and promising instruction candidates. Several MOIs are derived
from the symmetric encryption algorithms, i.e. AES and 3DES. As symmetric encryption is one
of the major bottlenecks in IPv6 processing [2], it is expected that those MOIs will improve the
performance of the IP stack application as well. Based on our profiling results indicating that
shift (sll/srl), xor, store(sw), and load (lw) operations are most frequently used in the encryption
algorithms, we select the MOIs as listed in Table I. Table II lists the number of IR nodes and the
number of MOI candidates (when Cburg is applied) for the largest basic block in each benchmark.
This roughly suggests the size and complexity of each benchmark for code generation.

The iterative approach is introduced because of the phase-coupling nature of our methodology, in
the sense that we first select the most profitable MOI candidates and then run them through an
additional MOI vs SOI round in the final tree covering. Thus what seems to be the best set of
MOI candidates may turn out to be less than the optimal after the final tree covering. However,

further suggest that our non-iterative version is as nearly efficient as the iterative version, at least
in all the cases we have seen.

8. CONCLUSION
We presented Cburg, a graph-based code-generator generator. With an increasing use of applicationspecific architectures, unconventional instructions such as MOIs are becoming an important target
to support. Cburg is the first approach to support MOIs and graph-based code selection in general
in the context of retargetable compilers. The general problem of code selection for MOIs relies on
the fact that at each IR-node a local decision has to be made which affects the global result of the
pattern matching process. The proposed formulas provide Cburg with a powerful cost metric that

is able to evaluate the quality of local decisions in terms of the global result by taking various costs
of MOI rules into account. Our experimental results on several applications from multiple domains
and DSP kernels demonstrate that Cburg can generate effective code selectors for various target
ISAs and can be used to quickly and accurately evaluate various ISAs at the whole application
level.
In the future we plan to integrate Cburg into more compilers to verify its reusability towards
different IRs and backends. Furthermore, the hardware cost that is associated with each MOI has
to be examined to evaluate the obtained speedup more accurately. Finally, an interesting open
issue is how to determine the most valuable set of instructions including MOIs in an automatic
fashion for a given set of applications, which will have much advantages over a manual and ad
hoc method as was done in this study.
